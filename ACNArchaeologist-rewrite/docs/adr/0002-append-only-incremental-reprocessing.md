# 增量产品使用不可覆盖的重新处理记录

## 背景

增量产品可能因为程序错误而抽取失败，也可能通过机器检查后被审核人发现内容边界错误。修复程序后需要再次处理，但上游输入并没有因此产生新变化。如果覆盖旧 Payload 或审核决定，就无法再说明审核人当时拒绝了什么；如果创建新的变化 Batch，又会错误表示上游提供了一轮新快照。

## 决定

1. 修复程序后，在原增量 Batch 下为该产品新增一份不可覆盖的重新处理记录。
2. 新记录复用原 Batch 固定的中文、英文 HTML、`soft-category.json` 和 Product Definition 投影，不读取当前上游目录，也不推进全局对比基准。
3. 每份记录拥有新的运行名、Payload、L3a、L3b、审核清单和审核决定；以前的文件和决定保持不变。
4. 最新结果未通过机器检查时可以直接重新处理；最新结果已通过机器检查时，必须提供拒绝该结果的真实审核决定。
5. 每次拒绝只能对应它实际审核的那份处理记录，不能重复用于更新后的结果。
6. 多次重新处理形成从原 Batch 开始的唯一顺序，只有最新记录能够进入 Delta Release。
7. 若当前 Product Definition 的页面类型、Strategy 或双语路径已经变化，停止同一固定输入重新处理，另行判断新的输入变化范围。

## 理由

这个边界同时保留了两类事实：原增量 Batch 说明为什么产品需要处理，每一份重新处理记录说明某一版程序对同一输入产生了什么结果。它允许修复代码，却不允许修复动作改写历史或混入新的上游输入。

## 影响

- 普通拒绝、机器失败和重新处理都不会结束原增量 Batch。
- 审核页面会同时显示原增量 Batch 和当前重新处理记录，审核人针对最新双语结果作决定。
- 旧结果即使后来被批准，也会因不是最新记录而被 Delta Release 排除。
- 输入复制中断后可以继续，继续时仍从原 Batch 固定输入恢复。
- 只有最新双语结果完成交付，或审核人明确结束而不交付，产品才从原 Batch 中解决。
