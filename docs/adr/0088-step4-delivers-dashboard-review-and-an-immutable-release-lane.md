# Step 4 Delivers Dashboard Review and an Immutable Release Lane

Status: Accepted

Step 4 must finish a usable daily loop rather than stop after machine evidence. Every machine-passed Batch Item enters the Review Queue as pending. The approval unit is one Resource Key and language; an item that was not reviewed is not implicitly approved because another item or another language was sampled.

The Dashboard evolves from a read-only capability ledger into the local review workbench. It presents capability, execution, Machine Validation, review, evidence binding, release eligibility, and publication as separate dimensions. Reviewers use it to inspect frozen Source and persisted Payload evidence, record the states they checked, and request an approved or rejected transition. Dashboard code must invoke the same controlled review service or command used by the CLI; it must never directly edit projection JSON or become a second state authority.

Review decisions are append-only and bind the reviewer, time, item identity, Source hash, Payload hash, validation evidence hash, inspected states, verdict, reason classification, and notes. The revisioned batch-manifest.json remains the lifecycle and item-state authority. A changed bound hash makes the previous decision stale and requires a new review. Machine failure cannot be overridden by a human decision. Step 4 Approval Eligibility requires successful execution, passed Machine Validation, current matching evidence, valid inspected states, and no unresolved Source Quality Finding; an unresolved finding remains pending or is rejected for upstream correction. Step 5 adds formal disposition and visual-review blocker workflows through a new Profile.

Only items with successful execution, passed Machine Validation, Approval Eligibility, a current approved Review Decision, and matching evidence hashes may be copied from canonical runs/{batch_id}/outputs into a write-once output/releases/{release_id} directory. One Release contains items from exactly one Batch Run. It is sealed by atomically finalizing a canonical Release Manifest that binds every included payload, decision, Sampling Profile, Sampling Plan, and hash; any post-seal drift invalidates it. Upload accepts this sealed Release rather than scanning an arbitrary output directory, and publication is recorded only after successful delivery. Pending, rejected, stale, blocked, failed, or experimental artifacts cannot enter a Release.

Step 5 deepens this minimum lane with Machine Validation Report 2.0, formal Source Finding Disposition, richer approval blockers, and complete Complex Table visual-review governance. Those additions apply through a new frozen profile and do not retroactively rewrite a completed Batch Run.

This decision supersedes ADR-0086's prohibition on Dashboard review operations and basic longitudinal growth views while preserving its rule that Dashboard projections are not authorities. It also supersedes the Step 4 timing and scope in ADR-0024, ADR-0025, and ADR-0067; their detailed visual-review techniques are deferred to Step 5. ADR-0004, ADR-0005, ADR-0007, and ADR-0069 remain in force: queue membership, Approval Eligibility, Review Decision, Release membership, and Publication stay separate, and `complex_table_visual_review_required` exists only for a Step 5 Profile that activates it.
