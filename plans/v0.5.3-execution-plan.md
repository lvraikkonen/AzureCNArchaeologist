v0.5.3 只扩展当前四类 Core 8 和两个 carry-over 所需能力。不得为了未来未知产品预建通用插件系统、DSL、注册中心、生命周期框架、复杂兼容层或多套平行 truth source。优先复用现有实现和成熟库，以最少的新抽象满足当前验收标准。

## 1. 目标、保证边界与工程原则

v0.5.3 只完成五项产品目标：

1. 在同一个新的 current full bilingual Batch 上，为 4 个 Core 产品 × 2 种语言形成完整的 Core 8 L3b 正/负证据覆盖；
2. 对 `en-us/time-series-insights` 与 `zh-cn/sla-sql-data` 给出 Core 8 分母之外的明确 qualification 结论和后续 owner；
3. 在现有 `/review` Workbench 内展示 L3a/L3b、Source、Expected、Payload 和 diff，不建立第二套人工审核 lifecycle；
4. 根据正式证据形成并接受 Machine Gate policy 决策，但本版本保持 `runtime_effective=false`；
5. 运行当前完整双语 Batch，形成并人工接受残余问题地图，随后再冻结 v0.5.4–v0.6 的问题组顺序。

以下保证边界始终成立：

- L3a `strategy_replay_consistency` 与 L3b `independent_source_content_fidelity` 是两个独立 claim，各自展示 verdict、coverage、binding 和 evidence；
- `failed`、`blocked`、`not_qualified`、`not_run` 与 missing 不得汇总成 passed；L3b passed 也不能覆盖 L3a failure、Source blocker 或人工 rejection；
- 当前 Machine Gate、Review Decision、Approval Eligibility、Release、upload 和 publication 的运行时行为不变；
- Workbench 只展示 Evidence，人工批准仍由现有 L4 Review Decision 与 `inspected_states` 承载，不增加人工 L3b 状态；
- Business Payload 不增加 L3b、validation、quality 或 source 字段；
- accepted v0.5.2 artifact、tag、Batch 和 reports 不回写、不移动、不重新裁决；
- 本阶段不 build Release、不 upload、不 publish、不 push、不 merge、不创建 PR。

工程实现遵循三条原则：

- 内容 verdict 来自直接语义比较和可读 diff；hash 仅用于既有 manifest provenance、最小 Evidence 完整性和历史防篡改；
- 优先选择满足当前目标的最小实现，没有当前消费者时不新增框架、Schema、renderer、兼容层或 lifecycle；
- 防御性检查集中在 CLI/用户输入、持久化 artifact、路径安全、binding 和历史不可变边界；边界内已验证对象不重复执行同类检查。

### 2.2 Core 8 与实际 required scope

Core 8 固定为：

| 页面族 | Core items | 当前 snapshot 的预期 scopes | 当前预期合计 |
|---|---|---:|---:|
| `region_filter` | `zh-cn/api-management`、`en-us/api-management` | 每语言 5 个 interactive scopes | 10 |
| `complex` | `zh-cn/cloud-services`、`en-us/cloud-services` | 每语言 15 个 interactive + 1 个 page-global | 32 |
| `simple_static` | `zh-cn/service-bus`、`en-us/service-bus` | 每语言 1 个 full-content | 2 |
| `support_article` | `zh-cn/icp-faq`、`en-us/icp-faq` | 每语言 1 个 full-content | 2 |
| **合计** | **8 language-level items** | — | **当前预期 46** |

scope 使用可读、确定性的 key，不通过 hash 生成业务 identity：

- RegionFilter：`interactive:region=east-china2`；
- Complex：`interactive:region=east-china2|category=tabContent1-1`；
- page-global：`page_global`；
- SimpleStatic 与 SupportArticle 正文：`full_content`。

interactive key 按页面族定义的筛选维度顺序拼接，value 来自 Source control 的机器值。当前 snapshot 预期 API Management 每语言 5 个 Region，Cloud Services 每语言 5 个 Region × 3 个 Category，另有一个 page-global scope；这只是 preflight 预期，不是永久硬编码分母。

正式分母必须由新 Batch 实际绑定的 Source 按已冻结规则重新推导为 `formal actual scope universe`。若 item membership、页面族、claim 和 scope 推导规则不变，但实际 Region/Category 数量使 Core denominator 不再等于当前 preflight 预期 46，应暂停正式 record、展示差异并由人工确认；无需仅因正常 Source 变化重写整份计划。

Core 8 的每个 item 都必须完成 qualification，覆盖实际推导出的全部 required scopes，并形成 `passed`、`failed` 或 `blocked` 正式 bundle。Core item 为 `not_qualified`、`not_run`、binding fatal 或缺少 required scope 时，v0.5.3 不能接受。

### 2.3 两个分母外 carry-over

| item | 页面结构 | 当前 snapshot 的预期 scopes | 合法结论 |
|---|---|---:|---|
| `en-us/time-series-insights` | Region × Category Complex | 4 interactive | `passed` / `failed` / `blocked` / `not_qualified` |
| `zh-cn/sla-sql-data` | 带历史 route map 的 SupportArticle | 1 full-content | `passed` / `failed` / `blocked` / `not_qualified` |

两项均不进入 Core 8 item 分母或 Core scope 分母。若 qualified，则生成并保留相应正式 bundle；若 `not_qualified`，qualification 结果必须说明原因、当前缺失能力和后续 owner，不伪造 Evidence。

表中的 4 / 1 scopes 只是当前 snapshot 的 preflight 预期。对 qualified carry-over，正式 required scopes 同样必须由新 Batch 实际绑定的 Source 按相应页面族规则推导，生成的 bundle 必须覆盖全部 formal actual required scopes。carry-over 的实际 scope 数量不计入 Core item/scope denominator，但必须作为 `carry-over qualification scopes` 在 qualification、Evidence 和最终汇总中单独记录。

### 2.4 明示 `en-us/icp-faq` 的 `claim_limitations`

`en-us/icp-faq` 当前实际绑定复用中文 Source snapshot。它的 L3b 只能证明英文 item 的 persisted payload 与其实际绑定 Source 一致，不能证明英文翻译、语言正确性或本地化质量。该 `claim_limitations` 必须进入 persisted Evidence、Workbench、人工复核记录和 Machine Gate decision，不能只留在计划说明中。

`claim_limitations` 限定某个 L3b verdict 能够证明的范围，但不自动改变内容比较 verdict。一个 item 可以在存在 `claim_limitations` 时得到 `passed`；该结果只能在所声明的 claim 边界内解释。因此 `en-us/icp-faq` 的 Source reuse 不自动使 item 变为 `not_qualified` 或 `blocked`，不自动生成 Approval blocker，也不得被解释为英文语言质量通过。

### 2.5 Machine Gate 只裁定、不激活

Machine Gate 决策必须由正式覆盖率、失败类型、carry-over qualification、`claim_limitations`、L3a/L3b disagreement 和人工复核共同得出。合法结论包括：

- `parallel_only`：L3b 继续并行记录，不进入 Machine Gate；
- `qualified_scope_candidate`：建议未来只对明确 qualified 范围启用；
- `phased_activation_candidate`：建议未来先 shadow/observe，再按条件分阶段启用。

无论选择哪一种，v0.5.3 均记录 `runtime_effective=false`，不修改当前 Review、Approval Eligibility、Release 或 upload 行为。如果未来版本实施 gate activation，应在该版本的 execution plan 中定义必要的 runtime contract 和 migration；v0.5.3 不预先建设。

## 3. 计划语义冻结与 Batch binding

### 3.1 Plan freeze 固定什么

Plan freeze 只固定：

- Core 8 和两个 carry-over 的 item membership；
- `region_filter`、`complex`、`simple_static`、`support_article` 四个页面族；
- L3b claim 覆盖的内容字段与排除项；

- 独立 runtime 的禁止调用边界；

L3b claim 覆盖 qualified Pricing 的 `contentGroups[].content`、具有可证明 Source 边界的非空 `baseContent`，以及 SupportArticle 的 `mainContent`。`commonSections`、标题/SEO metadata、CSS/JavaScript runtime semantics、CMS portability、最终模板渲染和 publication 不在本 claim 内。

### 3.2 新 Batch 冻结什么

实际 Source snapshot、Product Definition、适用 config/route map、persisted payload、source-proven scope universe 和 producer commit 是运行输入，由新 Batch 的现有 manifests 和每项 Evidence 记录。Execution Plan 不复制这些会正常变化的字节身份。

保留的前置 provenance 只有：

- `v0.5.2` tag/commit；
- v0.5.1 reference Batch `20260811T171630Z-e80afabe`；
- 第 2.1 节列出的 v0.5.2 accepted bundle 与报告位置。

普通 HTML 快照、Product Definition、`soft-category.json` 或 route-map 内容更新属于 Batch 输入变化，不自动触发 plan amendment。只有 item membership、页面族或策略语义、scope 推导规则、L3b claim 边界或独立核对可行性发生实质变化，才需要修订计划。

### 3.3 P0 preflight

正式实现前执行一次简明的计划前置检查：

1. 确认 Core 8 与两个 carry-over 的 membership；
2. 读取当前预计进入下一 Batch 的 Source、Product Definition 和适用 config/route map；
3. 按已冻结的页面族和 scope 推导规则，形成 `preflight expected scope universe`；
4. 显示其相对当前 Core 46 scopes、carry-over 4 / 1 scopes 预期的变化；
5. 确认四页面族、L3b claim、scope 推导规则和独立核对可行性仍成立；
6. 不绑定 payload、不记录 formal producer commit、不形成正式 denominator，也不生成正式 Evidence。

P0 preflight 只用于确认当前计划仍可执行。正式 Source/config/payload binding、producer commit 和 `formal actual scope universe` 必须在新 Batch 完成后，由 P4 从该 Batch 的 manifests 重新读取和冻结。

## 4. 最小 contract delta 与实现形态

### 4.1 字段缺口驱动的持久化 contract

只对 persisted artifact 确实无法表达的字段创建 successor，不因版本编号一致性连带升级 contract。

字段缺口检查必须双向进行：

1. 检查四页面族、scope kind、payload locator、`claim_limitations` 和 SupportArticle route-map basis 是否存在 1.0 无法表达的新字段；
2. 检查 1.0 是否强制要求当前 bundle 已明确不再生成的 projection/UI artifact 或 identity。

本轮只读 contract 核对已确认三项彼此独立的实际缺口：

- Profile 1.0 将页面族限定为 `controlled_fixture` / `region_filter`，并固定旧算法与 transform 范围，无法表达本计划四页面族的验证方法；
- Basis 1.0 的 state basis 没有 `scope_kind`、`payload_locator` 或可表达 SupportArticle 独立 route-map reconstruction basis 的结构；
- Evidence 1.0 使用旧字段 `qualification_limitation`，强制 `review_projection_artifact_identity`，且没有 `scope_kind`、`payload_locator` 和 `claim_limitations`。

因此在当前 1.0 bytes 下，Profile、Basis 和 Evidence 各自都需要最小 add-only successor；这是三个已验证 gap 的分别结论，不是“三套 contract 必须一起 bump”的预设。P1 先确认这些 1.0 contract 未漂移，再只实现以下必要表达：

- `scope_kind`：interactive、page-global 或 full-content；
- `payload_locator`：`contentGroups[].content`、`baseContent` 或 `mainContent`；
- `claim_limitations`；
- SupportArticle route-map reconstruction basis。

不得为了复用 Evidence 1.0 而恢复持久化 Workbench projection，也不得省略 required 字段却继续宣称符合 1.0。若 P1 核对发现上述事实已有漂移，只按同一双向 gap 规则调整实际受影响的 persisted successor，不扩大到无关 contract。

Profile 只描述“如何验证”，target set 只描述“本次验证谁”，两者分开；Profile 不绑定本次具体 item 列表。必要 fragment 可继续由 Evidence 引用，Workbench 从 canonical Evidence、Basis 和 fragment 在内存生成 view model，不新增 `review-projection.json`、持久化 Workbench view artifact 或额外 UI artifact identity。

Workbench HTTP response 是仓库内部接口时，前后端可在同一变更中直接更新；只有代码核对发现真实仓库外消费者时才引入版本兼容。唯一无条件保留的兼容边界是：v0.5.2 accepted bundle 保持原字节并继续由只读 reader 验证。

现有 verdict-relevant algorithm identity 仍限于 reconstruction profile、wire transform 和 comparison 三类。只 bump 实际发生语义变化的版本，不为了编号一致全部升级，也不增加第四类 identity。格式化 diff 或 UI 展示不影响内容 verdict。

### 4.2 薄共享函数与四个明确 adapter

在现有 `src/independent_fidelity/` 上增加当前目标所需的四个 adapter：

- `region_filter`：API Management 双语状态、desktop authority、mobile machine-domain cross-check 和 soft-category ownership；
- `complex`：Cloud Services 双语 Region × Category、page-global boundary 和 table ownership；
- `simple_static`：Service Bus 的唯一正文边界和必要 wire transform；
- `support_article`：ICP/SLA 正文边界、UI-only node 排除、URL 与 route-map reconstruction。

共享层只提供当前多处真实使用的薄函数，例如 `bind_batch_item`、`record_bundle`、`verify_bundle`、`aggregate_item_verdict`。不建立 page-family registry、通用 verifier service、DSL、未来全目录平台或只为旧内部 helper/CLI 存在的 wrapper。

四个 adapter 必须从 Source 独立重建 Expected，不调用生产 Strategy、ExtractionCoordinator、reachability/projector、Region Processor、production cleaner、transform executor、payload builder 或生产 URL/route-map 实现。允许复用安全文件读取、成熟 parser/URL resolver、canonical JSON 工具和纯比较模型。

### 4.3 直接内容比较

每个 required scope 至少直接比较：

- 规范化 DOM 与节点结构；
- tag、文本、表格或正文顺序；
- 可见文本与有业务意义的属性/URL；
- state criteria、table ownership、正文 boundary 或 route-map 语义对象；
- 独立重建 Expected 与 persisted Payload 的可读 diff。

hash 可在既有 manifest 或 Evidence contract 需要时验证所读取文件未被替换，但不能替代上述比较。人工复核围绕内容、diff、verdict、coverage 和 `claim_limitations`，不围绕 fragment、diff 或 HTML 文件的一组 hash。

### 4.4 真实信任边界

以下检查保留并尽量只在边界执行一次：

- CLI/用户提供的 Batch、item 和 path 防 path traversal 与 symlink escape；
- persisted JSON 可解析并满足实际使用的契约；
- Source、payload、Batch、item 和 producer binding 一致；
- historical accepted bundle 不覆盖；正式写入使用临时目录、verify 后原子 promote；
- Source/Payload HTML 在 Workbench 中 escaped，不执行脚本，不作为可信 DOM 注入；
- 独立 runtime 不调用第 4.2 节禁止的生产实现；
- ownership、boundary 或 binding 无法可信建立时停止该 claim。

边界内已验证的对象直接传递，不在 binder、reader、service 和 UI bridge 重复计算同一 Schema/hash/binding。普通内容 mismatch 产生 `failed`；证据足以定位但不足以完成 claim 的结构问题产生 `blocked`；binding 或 contract 不可信时才是 fatal 且不生成 bundle。一个 item 的 mismatch 不应终止其余 target items。

5. 不冻结 current Source/config SHA，不生成正式 Evidence。

### P1：最小 contract delta 与四页面族 adapter

1. 完成 1.0 双向 contract gap 检查，只为真正不兼容的 persisted artifact 新增必要 successor；
2. 分离 validation Profile 与本次 target set；

### P2：高信号反证和 L3a/L3b policy 对齐

共享基础设施只测试一次：

- binding 不可信；
- atomic promote 与 no-overwrite；
- historical v0.5.2 bundle verify；
- escaped rendering；
- import firewall 与 runtime independence sentinel。

每个页面族保留少量高信号反证：

- RegionFilter：状态交换、少选；
- Complex：Region/Category 交换、page-global 越界；
- SimpleStatic：正文边界过宽、过窄；
- SupportArticle：正文边界漂移、URL route-map 错误。

同时核对生产 extraction、L3a strict projection 与 L3b 对唯一配置行内 duplicate table ID 是否都采用 first-occurrence ordered-unique。输出简短的 `reports/v0.5.3/l3a-l3b-soft-category-alignment.md`，确需自动汇总时可附一个小型 JSON；不为该报告建立 Schema。

若三条路径存在差异，必须记录具体 affected items/scopes、行为差异、风险和 owner。Machine Gate 不得把受影响范围静默视为等价；合法决策可以是 `parallel_only`、明确排除受影响范围的 `qualified_scope_candidate`，或带修复/观察前置条件的 `phased_activation_candidate`。限定范围 candidate 必须显式列出 included/excluded profiles、items 或 scopes，受影响 scopes 不得被计为 gate-ready，也不得用总通过率掩盖局部 lane 差异；v0.5.3 仍保持 `runtime_effective=false`。

测试不在每个页面族重复 target、qualification、六种 verdict 和损坏状态的完整组合；以共享边界测试加页面族高信号反证覆盖真实风险。

### P3：Workbench Evidence panel

1. 在现有 `/review` 加入 GET-only L3b Evidence 数据和面板；
2. 从 canonical Evidence、Basis 和必要 fragment 生成内存 view model；
3. 并排显示 L3a/L3b claim、verdict、coverage，以及逐 scope Source、Expected、Payload、diff、criteria、locator、ownership、transform、reason 和 `claim_limitations`；
4. 区分 passed、failed、blocked、not-recorded 和 invalid，不把缺失显示为 pass；
5. 将 fragment 作为 escaped text/code 渲染，不执行 HTML、不 iframe 离线报告；
6. 不新增人工 L3b lifecycle，不改变 Review Decision、`inspected_states`、manifest revision、Approval Eligibility 或 Release contract；
7. 现有 L4 表单保持原样，查看 L3b panel 本身不得产生写操作。

server-level read-only mode 不是硬性交付。只有代码核对证明“查看 Evidence 会触发写操作且无法通过小改动隔离”时，才把它作为条件式 fallback。P3 测试只使用 fixture 或 temporary evidence。

### P4：正式 Batch、Evidence 与人工复核

P1–P3 的实现和适用测试全部提交，且 worktree clean 后，记录 formal producer commit，并运行：

```bash
uv run cli.py pipeline-run --all --language both --parallel-jobs 6
```

禁止 `--allow-dirty`。随后：

1. 从新 Batch manifests 读取实际 Source、Product Definition、适用 config/route map、persisted payload 和 producer commit；
2. 按新 Batch 实际绑定的 Source 重新推导 `formal actual scope universe`，并分别记录 Core denominator 与 `carry-over qualification scopes`；若与 `preflight expected scope universe` 不同，先展示差异并由人工确认后再正式 record；
3. 为 Core 8 和 qualified carry-over 逐项生成 Evidence；一个 item failed/blocked 后继续其他 items；
4. 每个 bundle 生成后立即执行 verify；随后对同一 item、同一 Batch binding 再次执行 record 或 set-record，必须返回 `existing-current/read-only` 结果，并且不得重写、修补或重新 promote 已有 bundle；
5. no-overwrite 只需验证当前目标 item 的 canonical bundle 在第二次 record 前后保持不变，并结合受限写入根、canonical item prefix、临时目录原子 promote 和 historical bundle verify 证明 add-only；不得恢复整个 Batch 的 regular-file path + SHA inventory；
6. 复用现有 batch manifest、batch report 和 reference report 解释 current Batch 结果与重大 regression；必要时只增加 v0.5.3 窄用途汇总；
7. 在 Workbench 人工只读复核全部 formal actual Core required scopes，以及所有已生成 carry-over bundle 的 actual scopes。

人工接受对象是：Batch ID、producer commit、Core item verdict/coverage、每项 canonical Evidence ID/path、全部 failed/blocked scopes、`claim_limitations` 和 carry-over qualification。人工不需要逐项接受 fragment、diff 或离线 HTML hash。

可信 `failed`/`blocked` bundle 必须进入 Evidence candidate 并保持不可变。Core item 的可信负证据可以约束 Machine Gate 决策，但不能被删除或改写成通过；Core item 无法 qualification 或没有正式 bundle 仍是版本 No-Go。

### P5：Machine Gate 决策、问题地图与收口

基于 P4 的真实结果生成：

- `reports/v0.5.3/machine-gate-decision.md`；
- `reports/v0.5.3/residual-problem-map.md`；
- `reports/v0.5.3/acceptance-status.md`；
- `reports/v0.5.3/v0.5.4-handoff.md`；
- 只有自动汇总确有需要时，才为前三项增加简单 JSON summary。

不为一次性决策和问题地图建立专用 Schema、renderer 或通用 Batch auditor。Machine Gate decision 必须记录实际 Core item/scope denominator、carry-over、L3a/L3b disagreement、`claim_limitations`、人工复核和 `runtime_effective=false`。残余问题地图必须列出 affected items、稳定失败证据、共享根因、风险、可安全修复点和排序理由。

`reports/v0.5.3/acceptance-status.md` 至少清楚分开 `implementation_status`、`evidence_coverage_status`、`core_l3b_verdict_distribution` 和 `machine_gate_decision` 四个摘要，不为此建立新 Schema。它必须报告 8/8 item coverage、formal actual Core scopes 的 reviewed/total、passed/failed/blocked 分布和最终 policy 选择，不能把 `v0.5.3 accepted` 简写为“Core 8 passed”。

## 6. Recorder 结果矩阵

| 情形 | 行为 |
|---|---|
| 非 target 或 `not_qualified` | 不生成 bundle；返回清晰 reason 和 owner |
| binding/contract 不可信 | 不生成 bundle；返回保留原始原因的 fatal error |
| 可解释但无法完成 claim | 生成并保留 immutable `blocked` bundle |
| 内容直接比较不一致 | 生成并保留 immutable `failed` bundle |
| 全部 formal actual required scopes 一致 | 生成 immutable `passed` bundle |
| 已有有效 bundle | 再次 record 返回 `existing-current/read-only`，只执行只读 verify 且不重写；若损坏则清晰报错，不自动修补 |

输出以 verdict、coverage、Evidence ID/path、reason 和 `claim_limitations` 为主。set command 应继续处理相互独立的 target items，并报告逐项结果；聚合退出码不能替代逐项证据。

## 8. v0.5.3 验收标准

v0.5.3 只有同时满足以下条件才可接受：

1. Core 8 membership、四页面族、claim 边界和 scope 推导规则与冻结计划一致；
2. 正式 Batch 来自已提交、适用测试通过且 worktree clean 的 implementation commit；
3. 每个 Core item 覆盖新 Batch Source 推导出的全部 formal actual required scopes，并形成 `passed`、`failed` 或 `blocked` 正式 bundle；
4. 两个 carry-over 均有明确 qualification、reason 和 owner；qualified carry-over bundle 覆盖其全部 formal actual required scopes，并作为 `carry-over qualification scopes` 与 Core denominator 分开记录；
5. L3a/L3b 分轨展示，内容 verdict 来自直接 DOM/结构/文本/顺序/ownership/语义比较和可读 diff；
6. v0.5.2 accepted bundle 保持字节不变并继续只读 verify；
7. Workbench 展示 L3a/L3b 与 Source/Expected/Payload/diff，不新增 lifecycle、不执行 raw HTML，也不改变现有 L4/Release 行为；
8. independent runtime 不调用禁止的生产 Strategy、reachability、projection、cleaner、transform executor 或 payload builder；
9. 正式 `failed`/`blocked` bundle 保持不可变；对同一 item/binding 第二次 record 返回 `existing-current/read-only`，当前目标 bundle 保持不变；binding/ownership/boundary 不可信时不伪造 claim；
10. 全部 formal actual Core required scopes，以及所有已生成 carry-over bundle 的 actual scopes，均已在 Workbench 完成人工只读复核；复核结论、全部 failed/blocked scopes 和 `claim_limitations` 已记录。基于这些结果形成的 Machine Gate decision 获人工接受，并明确 `runtime_effective=false`；
11. residual problem map 与 v0.5.4–v0.6 顺序获人工接受，`en-us/icp-faq` 的 `claim_limitations` 明示；
12. 适用测试、Dashboard、历史基线/reference verification、文档检查、版本/tag 和 clean-tree gate 全部通过。

`v0.5.3 accepted` 表示 Core 8 已取得完整可信的 L3b 正/负证据覆盖、carry-over 已明确裁定、Workbench 已有 Evidence panel，且 Machine Gate policy 与问题地图已获接受。它不表示全部 Core item 均 passed、全目录已支持 L3b、gate 已激活、L4 已批准、Release 已构建或内容已发布。

## 9. 暂停与停止条件

出现以下情况应停止实施并回到计划评审：

- Core/carry-over membership、页面族或策略语义、claim 边界或 scope 推导规则发生实质变化；
- 新 Batch 的 Source/payload/Batch/item/producer binding 不可信；
- 无法独立重建 required content、ownership、boundary 或 route map；
- 必须修改、移动或覆盖历史 accepted artifact 才能继续；
- 必须调用被禁止的生产实现才能形成 L3b claim；
- Workbench 必须改变 L4、Approval、Release 或 publication lifecycle 才能展示 L3b；
- 用户要求在 v0.5.3 内立即激活 Machine Gate；
- current Batch 出现无法解释的重大 regression；
- 适用测试失败，或 formal producer worktree 不干净。

普通 Source/config 更新不触发计划重写。formal actual Core scope 数量与当前预期 46 不同、但推导规则不变时，只暂停正式 record、展示 Core denominator 变化并请求人工确认。无论为何暂停，已经生成的可信 `failed`/`blocked` bundle 都不得删除或覆盖。

## 10. 建议提交顺序与 v0.5.4 handoff

提交按自然实现边界组织，不规定细粒度 provenance-only commit：

1. **Plan freeze**：只含获接受的 Execution Plan 与 ROADMAP；
2. **Contract/verifier/tests**：可按实际可复核边界拆分；
3. **Workbench**：Evidence panel 与测试；
4. **Evidence/decision candidate**：新 Batch Evidence、人工复核候选、Gate decision 和问题地图；
5. **Acceptance/version/tag**：人工接受后更新状态与版本，并创建 tag。

只有 formal producer commit 和最终 acceptance/tag commit 是必须精确记录的关键 provenance；其他提交以主题清晰、可复核为准。

v0.5.4 handoff 只交付：

- 同一 current Batch 上的 Core 8 Evidence set；
- 两个 carry-over 的 qualification；
- 实际需要的最小 persisted contract 与 historical reader；
- 现有 Workbench 的 L3b Evidence panel；
- accepted Machine Gate decision，且未提前激活；
- accepted residual problem map 和 v0.5.4–v0.6 顺序；
- 正负证据、`claim_limitations` 和人工复核记录。

v0.5.4 默认只实现 accepted residual problem map 的第一优先组。如果 v0.5.3 accepted Machine Gate decision 认为某项 activation prerequisite 应优先于该问题组，必须先在 v0.5.3 收口阶段同步更新并人工接受 ROADMAP 的版本主题和顺序，再编写对应 execution plan；不得仅由后续 execution plan 单方面改变 v0.5.4 主题，也不得借 v0.5.3 的接受扩大范围。
