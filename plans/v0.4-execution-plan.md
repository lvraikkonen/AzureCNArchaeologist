# v0.4 分支化、逐阶段执行计划

> 2026-08-03 状态：Step 0–3 已完成；Step 4 已完成 Slice A-D，包括 P3 Profile、抽样验证 runtime、Review Queue 2.0、append-only Review Decision service 与 CLI，以及本地 Dashboard Review Workbench。不可变 Release 和 upload gate 仍待后续切片。

## 1. 工作方式与决策顺序

- 开发分支保持为 codex/v0.4，不直接修改 master，不自动 push、merge 或创建 PR。
- 每个 Step 形成独立实现切片、测试门禁和提交；完成后暂停并汇报。
- 正式 Batch Run 默认要求 clean worktree；只有明确接受不可复现批次时才使用 allow-dirty。
- 任一门禁失败都保留真实失败状态，不用 warning、skip、known_unsupported 或重新抽样掩盖。
- ADR 是领域决策权威。ADR-0087 和 ADR-0088 对与旧 v0.4 方案冲突的范围具有最新优先级。
- 本计划描述目标能力；实际实现状态以代码、测试和 handoff.md 为准。

## 2. 必须保持分离的状态

| 维度 | 含义 | 典型状态 |
|---|---|---|
| Capability | Product Definition 是否属于系统正式支持范围 | supported / known_unsupported |
| Execution | 某个产品语言项是否成功生成 Payload | pending / succeeded / failed / skipped |
| Machine Validation | 自动化证据是否通过 | not_run / passed / failed |
| Human Review | 人工对当前哈希绑定证据作出的决定 | not_requested / pending / approved / rejected |
| Evidence Binding | 旧审核是否仍绑定当前 Source、Payload 和验证证据 | bound / stale |
| Approval Eligibility | 是否满足当前 Profile 的全部机器与证据门禁 | eligible / blocked |
| Release | approved artifact 是否已进入某个 sealed Release | not_released / released |
| Publication | 已批准产物是否已交付 | not_published / published |

Batch Item 是 Resource Key + Language。一个产品的中文批准不能替代英文批准；未被人工审核的项目保持 pending，不能因同批其他样本通过而隐式批准。

batch-manifest.json 是阶段、尝试和 item 状态的唯一生命周期权威。Validation、Review Queue、Dashboard、Batch Report 和 Release 视图均为受哈希约束的证据或投影，不得成为第二份状态真源。

## 3. Step 4 完成后的日常闭环

~~~text
上游 HTML + soft-category.json
  → data/current_prod_html 与 data/configs
  → 字节一致复制到 data/prod-html
  → 创建冻结 Batch Run
  → 策略抽取到 runs/{batch_id}/outputs
  → 全状态结构验证
  → 确定性分层抽样内容验证
  → machine-pass 项进入 Dashboard Review Queue
  → 人工 approved 或 rejected
  → approved 项生成不可变 output/releases/{release_id}
  → 校验 Release Manifest 后上传 Blob
~~~

源文件、配置、代码或验证 Profile 发生变化时创建新 Batch Run，不改写旧批次结论。

## 5. Step 4 / P3：抽样内容验证、Dashboard 审核与最小交付闭环

### 5.1 输入准备与批次冻结

1. 人工从上游取得最新 HTML，放入 data/current_prod_html 的相应中英文路径。
2. 将上游配置放入 canonical 路径 data/configs/soft-category.json。
3. 执行 catalog 和 source audit，拒绝缺失文件、错误语言路由、非法配置和身份漂移。
4. 将目标 HTML 字节一致复制到 data/prod-html；复制不转码、不修 HTML、不改变换行，Source 与 Normalized Input SHA-256 必须相同。
5. 创建新的 Batch Run，冻结本批次 item scope、Source、Normalized Input、Product Definition、soft-category、代码提交和 Profile 哈希。

上游获取本身仍是人工动作；Step 4 不建设网络抓取、自动修复或自动替换历史快照。

### 5.2 抽取

- Pipeline 继续把 canonical Business Payload 写入：
  - runs/{batch_id}/outputs/{language}/pricing/{resource}.json
  - runs/{batch_id}/outputs/{language}/SupportArticles/{articleType}/{resource}.json
- Diagnostic Sidecar 和其他运行证据保留在 runs/{batch_id}/diagnostics。
- 抽取失败只影响对应 Batch Item；该 item 不进入机器内容验证或人工批准。
- runs 下的 canonical 产物不得被 Dashboard、人工审核、Release staging 或 upload 原地改写。

### 5.3 机器验证的保证边界

机器验证由两层组成，并汇总为一个 categorical verdict。

**A. 全状态结构验证**

- 对完整 Source-proven Reachability Relation 中的每个状态执行 Step 3 CMS contract。
- 检查 filter topology、option identity、默认状态、criteria、唯一 contentGroup、missing/extra/duplicate state、inactive/placeholder/stale 内容和顺序。
- 这一层不抽样；任何状态的结构错误都使该 Batch Item validation=failed。

**B. 内容一致性验证**

- page-global metadata、baseContent 和 commonSections 执行完整比较。
- simple_static 的唯一主体状态执行完整比较。
- support_article 的文章主体执行完整比较。
- region_filter 和 complex 只对 Batch Item Sampling Plan 选中的 state-specific 内容执行比较。
- 每个选中状态比较冻结 Source HTML 与 persisted Payload 的完整展示内容，包括可见文本、价格和单位文本、表格内容、片段顺序、重复次数及必要 HTML 结构。
- 本阶段判断“抽取内容是否忠实于源”，不判断源价格是否符合外部商业系统，也不把表格行解释成 SKU。

通过意味着：全状态结构契约成立，且被选中的内容样本与源一致。它不意味着未抽中状态已经完成内容逐项对账。

### 5.4 Content Sampling Profile 与 Batch Item Sampling Plan

每个 Batch Run 先冻结可复用、版本化的 Content Sampling Profile，至少包含：

- profile_id 和算法版本；
- 各策略的 mandatory anchors、分层维度、总预算和每层最低覆盖；
- seed derivation；
- 状态数不超过预算时的全量比较规则。

Source Reachability 确定后、内容比较开始前，为每个 Batch Item 生成并冻结 Batch Item Sampling Plan，至少包含：

- Profile identity；
- 完整 state universe identity 与数量；
- derived seed；
- strata instances；
- exact selected state identities；
- plan SHA-256。

Profile 定义“如何选”，Sampling Plan 固定“本 item 实际选了什么”。`pipeline-validate` 必须重放两者，不得按当前可变文件重新抽签。

最小策略规则：

- 默认状态必须入样。
- RegionFilter 按 region 或源结构分层。
- Complex 按实际存在的 software、category、tab 或其他 parent branch 分层，不生成理论笛卡尔积。
- 随机次序由 frozen Source SHA、Batch Item identity 和 Profile identity 派生，不使用进程随机状态。
- Payload 哈希不参与抽样 seed，避免通过修改输出改变被检查状态。
- 相同 Source、item 和 Profile 必须得到相同样本。
- selected state 无法建立 Source 对照、解析失败或发生 mismatch 时直接失败；不得丢弃该样本再抽一个。

人工审核采用独立选择，不应只重复机器样本；优先检查机器未覆盖或风险较高的状态。

### 5.5 最小验证证据

每个 Batch Item 的 validation projection 至少记录：

- Machine Validation verdict 和稳定错误代码；
- Source、Normalized Input、Payload、soft-category、Profile 和 Sampling Plan SHA；
- 全状态结构检查数量与结果；
- coverage_mode=stratified_sample 或 full；
- universe、selected、untested state counts；
- seed、strata、exact selected states；
- 每个 selected state 的 Source/Payload fingerprint、结果和 diff reference；
- Step 4 Approval Eligibility 及当前 blockers；
- 是否有 warning，但不使用 quality_score。

证据必须明确写出抽样边界，不得使用 Full-State Content Fidelity、完整 Pricing Fact Fidelity 或 Commercial Price Accuracy 等过度声明。

### 5.6 Review Queue 与 Dashboard

Machine Validation 通过后，P3 Batch Item 进入 Review Queue 2.0，初始 review=pending。当前 CLI 已可读取队列：

~~~bash
uv run cli.py pipeline-review-list --batch-id <batch-id>
uv run cli.py pipeline-review-list --batch-id <batch-id> --status all --json
~~~

Slice D 已将现有 Dashboard 保持为 `/` 的只读 Capability Ledger，并新增本地 `/review` Workbench。Workbench 通过独立 Python loopback bridge 调用与 CLI 共用的 review domain service，不在托管 Dashboard 中提供写入口：

~~~bash
uv run cli.py pipeline-review-serve --batch-id <batch-id> \
  --dashboard-origin http://127.0.0.1:3000
~~~

Bridge 只绑定 loopback，要求显式 Batch allowlist，校验 Host、Origin、Bearer token、Content-Type、请求形状和 expected manifest revision。token 通过 Dashboard URL fragment 传入，前端读取后移除 fragment 并仅保存在内存中。没有 bridge token 时 `/review` 不读取或写入 Batch。

Dashboard 当前分为：

1. 总览：分别显示产品数和产品语言项数，以及 runnable、pending、approved、rejected、source-blocked、release-ready。
2. 审核队列：按策略、语言、类别、风险、失败历史、证据绑定和审核状态筛选。
3. 审核工作区：并列显示冻结 Source、Payload、机器样本和人工选择状态，记录备注和发现。
4. 失败与增长：按拒绝原因展示待处理项，并显示显式 history index、Release Manifest reference 和 Publication Receipt reference 的只读状态。

Dashboard 是受控操作入口而不是状态权威。批准和拒绝按钮调用当前 CLI 已共用的 review domain service；前端不得直接修改投影 JSON、review 文件或 manifest。状态成功落盘并由 projection 重建后才刷新显示。

### 5.7 人工批准与拒绝

Review Decision 使用 append-only 记录，并绑定：

- batch_id、Resource Key、Language；
- reviewer 和时间；
- Source、Payload、validation evidence SHA；
- 人工实际检查的状态组合；
- approved 或 rejected；
- reason classification 和 notes；
- 被替代的旧 decision identity（如有）。

当前 CLI：

~~~bash
uv run cli.py pipeline-review-decide --batch-id <batch-id> \
  --item-id zh-cn/api-management \
  --expected-revision <current-revision> \
  --reviewer reviewer@example.com \
  --verdict approved \
  --inspect-page-global \
  --inspect-state <reachable-state-id>
~~~

最小拒绝分类：

- upstream_source：上游 HTML 结构或内容问题；
- product_config：Product Definition 或 soft-category 配置问题；
- extractor_defect：抽取逻辑问题；
- validator_defect：机器验证漏报、误报或证据问题；
- needs_clarification：暂时不能安全判断。

批准条件：

- execution=succeeded；
- validation=passed；
- decision 绑定当前 Source、Payload 和 validation hashes；
- decision 中的 inspected states 属于本 Batch Item 冻结的 Reachability Relation；
- `approval_eligible=true`，且不存在未处置 Source Quality Finding 或其他当前 Profile blocker。

Step 4 不提供正式 Source Finding Disposition；发现未处置 Source Quality Finding 时保持 pending，或记录对应原因的 rejected，不能批准。机器失败不能被人工覆盖。Source、Payload 或验证证据变化后，旧 decision 显示 stale，必须重新审核。rejected item 不得进入 Release。

### 5.8 不可变 Release 与上传门禁（后续切片）

批准操作不移动 canonical run artifact。显式 promotion 从同一个 Batch Run 中的一个或多个当前 approved Batch Items 创建；一个 Release 不跨 Batch：

~~~text
output/releases/{release_id}/
├── release-manifest.json
└── payloads/
    ├── zh-cn/...
    └── en-us/...
~~~

Release Manifest 至少绑定唯一 Batch/Input Manifest、每个 payload path/hash、Validation/Sampling Profile、Batch Item Sampling Plan、sampled/total/untested coverage、validation evidence、Review Decision 和计划 Blob identity。

规则：

- Release 目录 write-once；同一 release_id 不覆盖。
- 在临时目录完成 payload 复制和哈希校验，最后 canonical serialize Release Manifest；以 manifest SHA + 全部 payload hashes 形成 seal，再原子 rename 为正式 release_id。
- seal 后任一文件、manifest 或 hash 漂移都使 `release-verify` 和 upload 拒绝。
- promotion 只复制 execution=succeeded、validation=passed、approval_eligible=true、review=approved 且哈希匹配的 item。
- pending、rejected、stale、machine-failed、known_unsupported 和 experimental artifact 均拒绝。
- upload 只接受 sealed Release Manifest，不递归信任任意 output 目录或 sidecar 状态。
- dry run 先展示计划；成功上传后才写 publication receipt，并将权威状态更新为 published。
- 上传失败保持 not_published，可对同一不可变 Release 幂等重试。

### 5.9 Step 4 失败处理

| 失败类型 | 处理 |
|---|---|
| 输入、路由或 SHA 错误 | 修正上游文件或配置，创建新 Batch |
| 上游 HTML 结构/内容问题 | rejected: upstream_source；保留证据并反馈上游 |
| 抽取或 contract 错误 | 修复 extractor，增加回归测试，创建新 Batch |
| sampled content mismatch | validation=failed；分析 Source、extractor 或 validator 原因，不重新抽样 |
| 人工发现机器漏报 | rejected: validator_defect；修复规则并补回归 |
| 审核不确定 | 保持 rejected 或 pending，不批准 |
| promotion/hash 失败 | 不生成 sealed Release，修复后重试 |
| upload 失败 | Release 不变，publication 保持 not_published |

### 5.10 Step 4 明确不做

- 不创建 PricingFact、CanonicalPricingTable、FactInventory 或 ApplicabilityMap。
- 不创建 StateProjectionMap、map registry、完整 Expected/Observed/Diff inventory 或 validation-context activation 工作流。
- 不对 RegionFilter/Complex 声称全状态内容一致。
- 不验证外部 Commercial Price Accuracy。
- 不建设完整 Report 2.0、正式 Source Finding Disposition 或全量 Complex Visual Review Variant。
- 不建设 Dashboard 多用户权限、任务分派、评论协作或公共托管。
- 不自动发布到 CMS；Blob upload 仍是显式受控动作。

### 5.11 Step 4 验收

- 四种策略的双语 Core Matrix 共 8 个 Batch Items 通过 unit、component 和 end-to-end。
- RegionFilter/Complex 对全部 source-proven states 执行结构契约，不因内容抽样遗漏 missing、extra、duplicate 或 misassigned group。
- 相同 Source/item/Profile 的两次执行产生相同 selected states、verdict 和 evidence hashes。
- sampled state 的文本、价格单位、表格顺序、multiplicity 或 state assignment 变化会失败。
- selected state 无法评估时失败，且不会 replacement draw。
- Dashboard 能展示独立状态、审核队列、证据、增长指标和失败原因。
- approve/reject 都生成 hash-bound append-only decision；Payload 变化使旧 decision stale。
- machine failure、approval blocker、review pending/rejected、stale binding 或 hash drift 均无法 promotion/upload。
- 至少各有一个 upstream_source、extractor_defect 和 validator_defect 的拒绝路径测试。
- approved item 可生成不可变 Release；同一 Release 可校验并幂等上传。
- 文档和 UI 明确声明 sampled/total coverage，绝不显示为 all states content passed。

建议提交切片：

1. docs: freeze converged step4 decisions
2. feat: add reproducible sampled content validation
3. feat: add controlled review decisions
4. feat: add dashboard review workbench
5. feat: add immutable release promotion and upload gate

每个切片通过自身门禁后暂停，不在一个提交中同时重做 validator、Dashboard 和 uploader。

## 6. Step 5 / P4：报告与质量治理深化

Step 5 在已经可日常使用的 Step 4 闭环上增强证据，不重新扩大 Step 4 的内容保证：

- Machine Validation Report 2.0 覆盖 normalize、preflight、extract 和 validate 的所有明确结果。
- 报告记录 Sampling Profile、sampled/total coverage、evidence hashes 和结构化 blocker taxonomy。
- 建立正式 Source Finding Disposition 和 Upstream Verification Report。
- 冻结 Desktop Rendering Profile，完成 Complex Table Visual Review、Visual Review Variant 和可复用证据。
- 以 cloud-services 双语证明完整视觉审核链路。
- Step 5 新门禁通过新的 Validation Profile 作用于新 Batch，不反向修改已冻结旧批次。
- 不重新引入逐项 Pricing Fact parser、完整 Applicability Map 或全状态内容 Inventory。

## 7. Step 6 / P5：可信测试体系与最终验收

- 保持 service-bus、api-management、cloud-services、icp-faq 双语 Core Matrix。
- Pricing Core 保留完整 Golden Payload，并新增/维护 Curated Sampling Baseline；SupportArticle 保留文章和 contract 基线。
- Baseline 更新只生成 reviewed candidate，普通测试不得自动覆盖。
- 默认测试完全离线；live interaction 仅作当前页面参考，不充当冻结 Batch Oracle。
- 两次 clean deterministic run 比较 Business Payload、state universe、selected state list、validation evidence 和 Release hashes。
- 全量 pipeline 保留真实 passed/failed；不能通过缩小分母伪造绿色。
