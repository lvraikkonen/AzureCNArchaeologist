# v0.4 分支化、逐阶段执行计划

> 2026-08-05 状态：Step 0–5 已完成；Step 6A 已建立双语 Core Fixture、Golden/Sampling Baseline、candidate/promotion 内部工具和 baseline 测试。Step 6B 的两次 clean Core deterministic runs、Step 6C 最终全量 Batch 与 Step 7 代表 Release 验收仍待完成。

## 1. 工作方式与决策顺序

- 开发分支保持为 codex/v0.4，不直接修改 master，不自动 push、merge 或创建 PR。
- 每个 Step 形成独立实现切片、测试门禁和提交；完成后暂停并汇报。
- 正式 Batch Run 默认要求 clean worktree；只有明确接受不可复现批次时才使用 allow-dirty。
- Machine Validation failure 和已分类的 approval-blocking finding 都保留真实失败/阻断状态，不用 warning、skip、known_unsupported 或重新抽样掩盖；Step 5 只能对已证明无歧义的 finding code 作显式 advisory 分类。
- ADR 是领域决策权威。ADR-0087 和 ADR-0088 对与旧 v0.4 方案冲突的范围具有最新优先级。
- Step 5 开始编码前先新增一份正式 ADR，冻结 Finding Code Policy、P3 successor contract 与 v0.4 scope reduction；ADR 编号按仓库当时的 next available number 分配，不在计划中预设。该 ADR 必须局部 supersede ADR-0012、ADR-0029、ADR-0030、ADR-0064 和 ADR-0088 的冲突范围，声明 ADR-0024/0025/0067 不会恢复，并保留 ADR-0070/0073/0074/0075 与 ADR-0088 的其余安全不变量。
- 本计划描述目标能力；实际实现状态以代码、测试和 handoff.md 为准。

## 2. 必须保持分离的状态

| 维度 | 含义 | 典型状态 |
|---|---|---|
| Capability | Product Definition 是否属于系统正式支持范围 | supported / known_unsupported |
| Execution | 某个产品语言项是否成功生成 Payload | pending / succeeded / failed / skipped |
| Machine Validation | 自动化证据是否通过 | not_run / passed / failed |
| Human Review | 人工对当前哈希绑定证据作出的决定 | not_requested / pending / approved / rejected |
| Evidence Binding | 旧审核是否仍绑定当前 Source、Payload 和验证证据 | bound / stale |
| Approval Eligibility | 是否满足 Machine Validation 与 Finding Code Policy 的批准前置条件；不包含 Human Review verdict 或 Evidence Binding | eligible / blocked |
| Release | approved artifact 是否已进入某个 sealed Release | not_released / released |
| Publication | 已批准产物是否已交付 | not_published / published |

Batch Item 是 Resource Key + Language。一个产品的中文批准不能替代英文批准；未被人工审核的项目保持 pending，不能因同批其他样本通过而隐式批准。

batch-manifest.json 是阶段、尝试和 item 状态的唯一生命周期权威。Validation、Review Queue、Dashboard、Batch Report 和 Release 视图均为受哈希约束的证据或投影，不得成为第二份状态真源。

## 3. Step 4 完成后的日常闭环

~~~text
上游 HTML + soft-category.json
  → data/current_prod_html 与 data/configs
  → 字节一致复制到 data/prod-html
  → 创建冻结 Batch Run

  → 全状态结构验证
  → 确定性分层抽样内容验证

~~~

源文件、配置、代码或验证 Profile 发生变化时创建新 Batch Run，不改写旧批次结论。

## 5. Step 4 / P3：抽样内容验证、Dashboard 审核与最小交付闭环

### 5.1 输入准备与批次冻结

1. 人工从上游取得最新 HTML，放入 data/current_prod_html 的相应中英文路径。
2. 将上游配置放入 canonical 路径 data/configs/soft-category.json。
3. 执行 catalog 和 source audit，拒绝缺失文件、错误语言路由、非法配置和身份漂移。
4. 将目标 HTML 字节一致复制到 data/prod-html；复制不转码、不修 HTML、不改变换行，Source 与 Normalized Input SHA-256 必须相同。
5. 创建新的 Batch Run，冻结本批次 item scope、Source、Normalized Input、Product Definition、soft-category、代码提交和 Profile 哈希。

上游获取本身仍是人工动作；Step 4 不建设网络抓取、自动修复或自动替换历史快照。

### 5.2 抽取

- Pipeline 继续把 canonical Business Payload 写入：
  - runs/{batch_id}/outputs/{language}/pricing/{resource}.json
  - runs/{batch_id}/outputs/{language}/SupportArticles/{articleType}/{resource}.json
- Diagnostic Sidecar 和其他运行证据保留在 runs/{batch_id}/diagnostics。
- 抽取失败只影响对应 Batch Item；该 item 不进入机器内容验证或人工批准。
- runs 下的 canonical 产物不得被 Dashboard、人工审核、Release staging 或 upload 原地改写。

### 5.3 机器验证的保证边界

机器验证由两层组成，并汇总为一个 categorical verdict。

**A. 全状态结构验证**

- 对完整 Source-proven Reachability Relation 中的每个状态执行 Step 3 CMS contract。
- 检查 filter topology、option identity、默认状态、criteria、唯一 contentGroup、missing/extra/duplicate state、inactive/placeholder/stale 内容和顺序。
- 这一层不抽样；任何状态的结构错误都使该 Batch Item validation=failed。

**B. 内容一致性验证**

- page-global metadata、baseContent 和 commonSections 执行完整比较。
- simple_static 的唯一主体状态执行完整比较。
- support_article 的文章主体执行完整比较。
- region_filter 和 complex 只对 Batch Item Sampling Plan 选中的 state-specific 内容执行比较。
- 每个选中状态比较冻结 Source HTML 与 persisted Payload 的完整展示内容，包括可见文本、价格和单位文本、表格内容、片段顺序、重复次数及必要 HTML 结构。
- 本阶段判断“抽取内容是否忠实于源”，不判断源价格是否符合外部商业系统，也不把表格行解释成 SKU。

通过意味着：全状态结构契约成立，且被选中的内容样本与源一致。它不意味着未抽中状态已经完成内容逐项对账。

### 5.4 Content Sampling Profile 与 Batch Item Sampling Plan

每个 Batch Run 先冻结可复用、版本化的 Content Sampling Profile，至少包含：

- profile_id 和算法版本；
- 各策略的 mandatory anchors、分层维度、总预算和每层最低覆盖；
- seed derivation；
- 状态数不超过预算时的全量比较规则。

Source Reachability 确定后、内容比较开始前，为每个 Batch Item 生成并冻结 Batch Item Sampling Plan，至少包含：

- Profile identity；
- 完整 state universe identity 与数量；
- derived seed；
- strata instances；
- exact selected state identities；
- plan SHA-256。

Profile 定义“如何选”，Sampling Plan 固定“本 item 实际选了什么”。`pipeline-validate` 必须重放两者，不得按当前可变文件重新抽签。

最小策略规则：

- 默认状态必须入样。
- RegionFilter 按 region 或源结构分层。
- Complex 按实际存在的 software、category、tab 或其他 parent branch 分层，不生成理论笛卡尔积。
- 随机次序由 frozen Source SHA、Batch Item identity 和 Profile identity 派生，不使用进程随机状态。
- Payload 哈希不参与抽样 seed，避免通过修改输出改变被检查状态。
- 相同 Source、item 和 Profile 必须得到相同样本。
- selected state 无法建立 Source 对照、解析失败或发生 mismatch 时直接失败；不得丢弃该样本再抽一个。

人工审核采用独立选择，不应只重复机器样本；优先检查机器未覆盖或风险较高的状态。

### 5.5 最小验证证据

每个 Batch Item 的 validation projection 至少记录：

- Machine Validation verdict 和稳定错误代码；
- Source、Normalized Input、Payload、soft-category、Profile 和 Sampling Plan SHA；
- 全状态结构检查数量与结果；
- coverage_mode=stratified_sample 或 full；
- universe、selected、untested state counts；
- seed、strata、exact selected states；
- 每个 selected state 的 Source/Payload fingerprint、结果和 diff reference；
- Step 4 Approval Eligibility 及当前 blockers；
- 是否有 warning，但不使用 quality_score。

证据必须明确写出抽样边界，不得使用 Full-State Content Fidelity、完整 Pricing Fact Fidelity 或 Commercial Price Accuracy 等过度声明。

### 5.6 Review Queue 与 Dashboard

Machine Validation 通过后，P3 Batch Item 进入 Review Queue 2.0，初始 review=pending。当前 CLI 已可读取队列：

~~~bash
uv run cli.py pipeline-review-list --batch-id <batch-id>
uv run cli.py pipeline-review-list --batch-id <batch-id> --status all --json
~~~

Slice D 已将现有 Dashboard 保持为 `/` 的只读 Capability Ledger，并新增本地 `/review` Workbench。Workbench 通过独立 Python loopback bridge 调用与 CLI 共用的 review domain service，不在托管 Dashboard 中提供写入口：


Bridge 只绑定 loopback，要求显式 Batch allowlist，校验 Host、Origin、Bearer token、Content-Type、请求形状和 expected manifest revision。token 通过 Dashboard URL fragment 传入，前端读取后移除 fragment 并仅保存在内存中。没有 bridge token 时 `/review` 不读取或写入 Batch。

Dashboard 当前分为：

1. 总览：Step 4 当前分别显示产品数和产品语言项数，以及 runnable、pending、approved、rejected、`source-blocked`、release-ready；Step 5 必须迁移到 `source_warning` / `approval_blocked` / `machine_failed` 的机器字段与 Source Warning / Approval Blocked / Machine Failed / Release Ready 的 UI 口径。
2. 审核队列：按策略、语言、类别、风险、失败历史、证据绑定和审核状态筛选。
3. 审核工作区：并列显示冻结 Source、Payload、机器样本和人工选择状态，记录备注和发现。
4. 失败与增长：按拒绝原因展示待处理项，并显示显式 history index、Release Manifest reference 和 Publication Receipt reference 的只读状态。

Dashboard 是受控操作入口而不是状态权威。批准和拒绝按钮调用当前 CLI 已共用的 review domain service；前端不得直接修改投影 JSON、review 文件或 manifest。状态成功落盘并由 projection 重建后才刷新显示。

### 5.7 人工批准与拒绝

Review Decision 使用 append-only 记录，并绑定：

- batch_id、Resource Key、Language；
- reviewer 和时间；
- Source、Payload、validation evidence SHA；
- 人工实际检查的状态组合；
- approved 或 rejected；
- reason classification 和 notes；
- 被替代的旧 decision identity（如有）。

当前 CLI：

~~~bash
uv run cli.py pipeline-review-decide --batch-id <batch-id> \
  --item-id zh-cn/api-management \
  --expected-revision <current-revision> \
  --reviewer reviewer@example.com \
  --verdict approved \
  --inspect-page-global \
  --inspect-state <reachable-state-id>
~~~

最小拒绝分类：

- upstream_source：上游 HTML 结构或内容问题；
- product_config：Product Definition 或 soft-category 配置问题；
- extractor_defect：抽取逻辑问题；
- validator_defect：机器验证漏报、误报或证据问题；
- needs_clarification：暂时不能安全判断。

批准与 Release 条件保持正交：

- execution=succeeded；
- validation=passed；
- `approval_eligible=true` 由 execution、validation 与当前 Approval Blockers 独立派生，不包含 Human Review verdict 或 Evidence Binding；
- `review=approved` 来自合法 decision，且 decision 绑定当前 Source、Payload 和 validation hashes；
- decision 中的 inspected states 属于本 Batch Item 冻结的 Reachability Relation，`evidence_binding=bound`；
- advisory Source Quality Finding 已在 CLI/Dashboard 中显著展示，并包含在当前 decision 所绑定的 validation evidence hash 中。

Step 4 的初始实现把每个 Source Quality Finding 都转换为 Approval Blocker；Step 5 将在最终 v0.4 规则中以 closed-world code policy 替换这一 blanket rule。Step 5 完成前不得把当前行为当作 v0.4 最终运营基线，也不得先跑最终全量 Batch。v0.4 不提供正式 Disposition、acknowledgment、override 或 exception 状态机。机器失败不能被人工覆盖；Source、Payload 或验证证据变化后，旧 decision 显示 stale，必须重新审核；rejected item 不得进入 Release。

### 5.8 不可变 Release 与上传门禁

批准操作不移动 canonical run artifact。显式 promotion 从同一个 Batch Run 中的一个或多个当前 approved Batch Items 创建；一个 Release 不跨 Batch：

~~~text
output/releases/{release_id}/
├── release-manifest.json
└── payloads/
    ├── zh-cn/...
    └── en-us/...
~~~

Release Manifest 至少绑定唯一 Batch/Input Manifest、每个 payload path/hash、Validation/Sampling Profile、Batch Item Sampling Plan、sampled/total/untested coverage、validation evidence、Review Decision 和计划 Blob identity。

规则：

- Release 目录 write-once；同一 release_id 不覆盖。
- 在临时目录完成 payload 复制和哈希校验，最后 canonical serialize Release Manifest；以 manifest SHA + 全部 payload hashes 形成 seal，再原子 rename 为正式 release_id。
- seal 后任一文件、manifest 或 hash 漂移都使 `release-verify` 和 upload 拒绝。
- promotion 只复制 execution=succeeded、validation=passed、approval_eligible=true、review=approved、evidence_binding=bound 且 decision 绑定全部当前 hashes 的 item。
- pending、rejected、stale、`validation=failed`、known_unsupported 和 experimental artifact 均拒绝。
- upload 只接受 sealed Release Manifest，不递归信任任意 output 目录或 sidecar 状态。
- dry run 先展示计划；成功上传后才写 publication receipt，并将权威状态更新为 published。
- 上传失败保持 not_published，可对同一不可变 Release 幂等重试。

已冻结命令：

~~~bash
uv run cli.py release-build --batch-id <batch-id> --release-id <release-id> --item-id <language>/<resource-key> --expected-revision <revision> --account-url <account-url> --container <container> [--prefix <prefix>]
uv run cli.py release-verify --release-manifest output/releases/<release-id>/release-manifest.json --require-batch-reference
uv run cli.py upload --release-manifest output/releases/<release-id>/release-manifest.json --dry-run
uv run cli.py upload --release-manifest output/releases/<release-id>/release-manifest.json --expected-revision <revision>
~~~

### 5.9 Step 4 失败处理

| 失败类型 | 处理 |
|---|---|
| 输入、路由或 SHA 错误 | 修正上游文件或配置，创建新 Batch |
| 上游 HTML 结构/内容问题 | rejected: upstream_source；保留证据并反馈上游 |
| 抽取或 contract 错误 | 修复 extractor，增加回归测试，创建新 Batch |
| sampled content mismatch | validation=failed；分析 Source、extractor 或 validator 原因，不重新抽样 |
| 人工发现机器漏报 | rejected: validator_defect；修复规则并补回归 |

| promotion/hash 失败 | 不生成 sealed Release，修复后重试 |
| upload 失败 | Release 不变，publication 保持 not_published |

## 6. Step 5 / P4：Source Finding 分级与 Approval Gate 收敛

### 6.1 目标

取消“所有 Source Quality Finding 一律阻止批准”的 blanket rule，但不放宽 Machine Validation，也不建设新的治理平台。Step 5 的唯一收口目标是：

> 对每个 emitted finding code 作小型、静态、fail-closed 的分类；让已证明不影响忠实重建的 advisory warning 可以进入现有人工审核与 Release 闭环，同时继续阻止真正有歧义或未知的风险。

### 6.2 Finding Code Policy

| 类别 | 最终行为 |
|---|---|
| Machine Validation failure | `validation=failed`；不进入人工批准，不能被降级或覆盖 |
| `advisory` | 完整保留并显著展示，不生成 Approval Blocker；machine-pass 且人工检查通过时可批准 |
| `approval_blocking` | `validation` 可独立为 passed，但 `approval_eligible=false`；保持 pending 或使用现有 reason 拒绝 |
| 未识别 finding code | fail closed，按 approval-blocking 处理，直到正式决策补充分类 |

分类原则：

- 只有冻结证据已消除状态、ownership、target、criteria 和内容歧义的问题才能是 advisory。
- 初始 advisory 只覆盖：严格 UTF-8 已通过时的 charset 声明问题，以及 desktop 仍为本语言事实源时的 mobile label 漂移。
- source-confirmed empty selection state 按 ADR-0074 保持 approval-blocking；没有正式 Disposition 时不能批准。
- `bilingual_source_reachability_drift` 等双语 source-proven state/topology 漂移保持 approval-blocking。
- structure、ownership、target、criteria、state mapping、selected-state comparison 等现有 validation error 继续 Machine Validation failure；不得为了扩大 advisory allowlist 把它们改造成 Finding。
- Step 5 的第一项工作必须盘点当前所有 emitted finding codes，并在 ADR、代码常量和参数化测试中一一枚举；文档中的示例不能替代完整 mapping。

兼容规则必须固定而不能依赖当前进程 registry。legacy fallback 白名单只包含当前唯一 review-capable pre-Step-5 tuple：`(id=v0.4-validation-p3, schema_version=1.2, path=data/configs/validation-profiles/v0.4-p3.json, sha256=fbbfa8bd937779748e86f48f738af5c561f164bf2e10615efe2515d45ba3ae1b)`。该 tuple 缺少 `finding_code_policy_identity` 时，读取与决策一律使用 `legacy-all-source-findings-block-v1`，保留“所有 Source Finding 都阻止批准”的语义：无 finding 的旧 item 在满足其他既有门禁时仍可审核/Release，任一 finding 则禁止 approve 但仍可 reject。P1/P2、未知/漂移 profile、旧 tuple 意外携带 policy、successor 缺少或损坏 identity 都必须 fail closed，不能利用 legacy fallback 降级；不得向旧 Batch 回填 identity，需要采用新 policy 时创建新 Batch。

v0.4 有意接受部分 `validation=passed` item 因 approval-blocking finding 无法进入 Release。这不是 incomplete adjudication，也不能通过人工 override、临时 reclassification 或未冻结的例外绕过；item 只能保持 pending，或以 `upstream_source` / `product_config` 等现有 reason 拒绝，修复 Source/config 后再创建新 Batch。新 ADR 的 Consequences 必须明确记录这一结果。

### 6.3 最小实现切片

#### Slice 5A：决策与 closed-world policy

- 新增正式 ADR：记录 blanket blocker 被替换的原因、完整 code mapping、unknown-code fail-closed 行为、允许 legacy fallback 的 pre-Step-5 frozen profile identity 白名单、旧 Batch 兼容边界和显式延后项。
- 在现有 Review/Approval precondition 层实现单一 Finding Code Policy；不新增第二份状态真源或通用规则引擎。
- 冻结 policy version/hash，并通过 code provenance、Validation Profile 1.3 P3-successor identity 与 Validation 2.1 evidence 进入新 Batch；不新建扩张内容保证的 P4 Profile，也不能只依赖无法从 artifact 追溯的进程内常量。
- advisory 继续出现在 `source_quality_findings[]` 和 Validation Evidence 中；只改变它是否产生 `approval_blockers[]`。
- Review Decision 继续绑定包含 Finding 的 validation evidence hash；v0.4 不升级 Review Decision schema 来保存额外 acknowledgment。
- policy 或证据发生变化时创建新 Batch；不得自动重算、改写或重新解释旧 Batch。
- 保持冻结的 P3 Profile 1.2 与 Pipeline Validation 2.0 文件字节和语义不变。Validation 2.0 要求任一 `source_quality_findings[]` 都使 source precondition blocked，不能原地修改其 schema/hash，也不能让 Review 层把同一份 blocked evidence 重新解释为 eligible。
- 为新 Batch 新增最小的 Validation Profile 1.3 P3-successor identity 与 Pipeline Validation 2.1 contract。Profile 1.3 必须以完整 tuple 显式继承上述 P3 1.2，保持 Content Sampling Profile、Sampled Content Evidence 1.0 和其他 P3 contract identities 不变，只把 pipeline validation 升为 2.1 并新增 canonical `finding_code_policy_identity`。Sampled Evidence 1.0 继续绑定 exact base P3 1.2；runtime 必须把 Sampling bindings 与 Validation 2.1 bindings 分开构造，Validation 2.1 再绑定 successor、policy 和原始 Sampled Evidence，禁止把 successor identity 塞入 1.0 后违反 frozen schema。Validation 2.1 evidence 必须投影同一 policy identity、绑定 Profile 1.3，且两者逐字段相等；Review/Release 只重放该冻结 identity，不读取 active registry 重新解释。2.1 按该 policy 生成 canonical source preconditions，允许 advisory finding 留在 `source_quality_findings[]` 而不产生 blocker。Step 6 normalized identities 由独立 comparison record 产生。这是兼容迁移，不增加 P4 内容、视觉或治理保证；successor exact id/path/hash 由新 ADR 冻结。
- policy resolver 必须是 version/profile-aware dispatcher，只接受两种组合：`Validation 2.0 + exact old P3 tuple + policy absent → legacy-all-source-findings-block-v1 blanket evaluator`，或 `Validation 2.1 + exact successor + Profile/evidence policy valid and equal → frozen-policy evaluator`。旧 P3 意外带 policy、successor 任一侧缺 identity、Profile/evidence mismatch、unknown profile 或 hash drift 全部 fail closed；Review 优先消费并复核 Validation 内 canonical preconditions，不把 raw findings 交给 active mapping 重解释。新 Batch 创建时 identity 无效则拒绝创建；冻结后 replay 发现 mismatch 时产生稳定 `finding_policy_identity_invalid` Machine Validation failure/诊断并禁止 Review/Release，不得算作 Approval Blocked 或 legacy fallback。不得回填旧 artifact。参数化测试固定 `legacy batch without policy identity → legacy blanket policy → not reclassified by current registry` 及完整 presence/mismatch matrix。

#### Slice 5B：CLI、Dashboard 与 accounting

- CLI 和 `/review` Workbench 在审核动作附近显著展示 advisory code、message 和 evidence path。
- Dashboard summary/filter 与 batch accounting 删除含糊的 `source-blocked` 聚合，并把三个结果作为独立维度。机器可读 JSON/schema 使用 snake_case 的 `source_warning`、`approval_blocked`、`machine_failed`（计数字段分别为 `source_warning_count`、`approval_blocked_count`、`machine_failed_count`）；UI 使用 `Source Warning`、`Approval Blocked`、`Machine Failed`、`Release Ready`。
- `source_warning_count` 是至少含一个 advisory finding 的 item 数，可与 `approval_blocked_count` 重叠；`approval_blocked_count` 是 `validation=passed` 且至少含一个 Approval Blocker 的 item 数；`machine_failed_count` 是 `validation=failed` 的 item 数，在最终 verdict 下与 `approval_blocked_count` 互斥。`release_ready_count` 只统计 `execution=succeeded + validation=passed + approval_eligible=true + review=approved + evidence_binding=bound` 且 decision 绑定当前 hashes 的 item，可与 `source_warning_count` 重叠。四个 count 是独立投影，不是总数可相加的互斥分区。
- approve 动作仍必须经过现有 review domain service；前端不得直接清除 blocker 或修改 manifest。
- Review Queue、Decision 和 Release contracts 仅做实现所需的最小 additive evolution；Validation 使用上述 versioned P3-successor contract，旧 2.0 保持只读。不创建 Report 2.0、Disposition 或扩张内容保证的 P4 Profile。
- 新增最小 Release Manifest 1.1 successor 以绑定 Profile 1.3、Validation 2.1 和 Finding Policy；旧 Release Manifest 1.0 的 bytes/schema 保持只读可验证。ReleaseService/StateStore/upload gate 按 manifest version closed-world dispatch，新 acceptance Batch 只能生成 sealed 1.1；Publication Receipt 1.0 可继续绑定已验证的 Release artifact，不另起新 receipt contract。
- StateStore 的 Profile→Projection closed-world routing、write-once/self-identity/profile-policy replay，ReviewService review-capable allowlist、Review Queue/Workbench projection 和 Release build/verify 必须同时识别 successor；禁止把 2.1 路由到 legacy Validation 1.0 或 mutable generic writer。Release build/verify 必须重放 bound Profile/policy 与 canonical validation preconditions；legacy item 即使出现异常 `review=approved`，只要含 finding 也不得 grandfather 进入 Release。

#### Slice 5C：针对性回归与文档同步（已完成）

至少覆盖：

- advisory + `execution=succeeded + validation=passed` + 无其他 blocker → `approval_eligible=true`，不依赖 Human Review verdict；
- 在 eligible 的基础上提交合法、current-hash-bound 的 Review Decision → `review=approved`；只有 `approval_eligible=true + review=approved + evidence_binding=bound` 才能进入 Release；
- machine-pass + 无 blocker + 无 decision / `evidence_binding=not_applicable` 仍为 eligible；eligible + rejected 保持 eligible/rejected，blocked + rejected 保持 blocked/rejected；stale binding 或 invalid inspected states 只影响 decision/binding 与权威 review 是否回 pending，不改变 Approval Eligibility；
- advisory 显著展示且 Review Decision 绑定含 warning 的 evidence hash；
- advisory + eligible + approved + bound/current hashes → 可进入 sealed Release；
- approval-blocking finding → 不能 approve 或 Release；
- 未识别 finding code → fail closed；
- Machine Validation failure → 人工仍不能覆盖；
- 当前 Batch 的 Source、Payload 或 validation evidence hash 漂移 → 旧批准 stale；policy 变化必须创建新 Batch，旧 decision 保留原 policy 下的历史语义而不被重新解释；
- pre-Step-5 legacy Batch 缺少 policy identity → 使用 `legacy-all-source-findings-block-v1` 的 blanket policy，不被 current registry 重分类，也不回填 identity；
- old/successor policy presence 与 mismatch matrix、successor routing，以及 legacy `approved + finding` 仍被 Release 拒绝；
- Dashboard/CLI/accounting 按上述 overlap 与互斥规则分别报告 warning、approval blocked、machine failed 和 release ready。

已同步更新 ROADMAP、execution plan、handoff、ADR、必要的 README/CONTEXT 和用户可见文案；Step 5 到此收口，下一步进入 Step 6 / P5 Core Matrix、golden baseline 与确定性验证，不自动启动 full batch。

### 7.2 两次 clean Core deterministic run

在相同冻结 Source、Product Definition、soft-category、代码和 Profile 上独立运行 8 个 Core Batch Items 两次，并比较：

- Business Payload artifact SHA-256；
- clean code provenance（相同 `git_commit` 与 immutable/worktree fingerprint，排除 captured time）以及每 item Product Definition、Source、Normalized Input 和 frozen soft-category SHA；
- source-proven state universe identity 和 ordered state identities；
- exact selected state identities 与 Sampling Plan `plan_sha256`；
- `sampled_content_semantic_sha256` 与 `validation_semantic_identity`；
- Finding Code Policy identity、分类结果与 Approval Eligibility inputs；
- promotion predicate 所需的当前 Source、Payload、validation、sampling evidence identity bindings。

`sampled_content_semantic_sha256` 与 `validation_semantic_identity` 是 `core-determinism-comparator-v1` acceptance record 新增的、版本化 normalized comparison identities，不是现有 artifact 字段或 `evidence_sha256` 的别名；二者都是对带 normalization algorithm version 的 closed-world whitelist object 计算的 lower-case SHA-256。record 外层可保存 left/right `batch_id` 用于 provenance，但不把它们纳入 semantic digest，也不成为 lifecycle state authority。comparator 先硬校验 clean code provenance、Product Definition、Source、Normalized Input、soft-category、Profile 与 Policy hashes 相同；sampled normalized object 再覆盖 mode/coverage、全状态 structure status、page-global fingerprints/verdict、适用时的 full-content fingerprints/verdict、state universe/default/ordered/selected identities、Sampling Plan `plan_sha256`、per-selected-state fingerprints/verdict，以及稳定 error/finding codes。无 Sampling Plan 或 full-content comparison 时写入显式 `null/not_applicable`，不能省略字段。validation normalized object 引用 `sampled_content_semantic_sha256`，并加入 validation verdict、finding `{code, semantic path, classification}`、canonical approval preconditions 与稳定 error codes，不引用 raw evidence hash/path。明确排除 `generated_at`、Manifest revision、attempt identity、artifact storage path、包含运行路径的 message 和其他运行元数据。Business Payload artifact SHA-256 是唯一直接跨 Batch 比较的业务 artifact SHA；Sampling Plan 比较 `plan_sha256`，Plan/Sampled/Validation 的外层 artifact SHA 与现有 Sampled/Validation `evidence_sha256` 只在各自 Batch 内证明文件完整性与 current binding，不能替代 normalized identity。跨 Batch 也不得直接比较包含 `validation_artifact_sha256` 的完整 Review/Promotion binding object，只比较规范化 identities，并分别证明两个 Batch 各自 binding current。

Step 6 不要求为了比较而预先制造 Review Decision 或 Release。实际 approve/reject 和 Release build/verify 留在 Step 7；两次 Core run 只需证明业务身份、分类结果和 promotion predicate inputs 等价。

- 提交 Acceptance Report、其他 acceptance artifacts 与 version bump；
- 在该 acceptance commit 后执行最终 clean-tree check，只有工作树干净时才冻结 v0.4 baseline/tag；
- 暂停并交付分支摘要，不自动 push、merge、创建 PR 或对外发布。

### 8.6 Post-v0.4 进入门禁

v0.4.0 冻结后再执行整体 Post-Implementation Review 和 Roadmap Re-baseline；它是 v0.5 Spec 的进入门禁，不是 v0.4 acceptance 的组成部分。该 Review 只重新校准 v0.5–v0.7 的近期主题、顺序和范围，不重新打开 v0.8 架构清理、v0.9 Release Candidate 与 v1.0 稳定版的长期方向。Review 必须用最终 full-batch、人工审核工作量、失败结构簇和现有报告/Workbench 实际使用数据判断：

1. 主要瓶颈是解析覆盖率还是审核治理；
2. 现有报告是否已足够，Report 2.0 是否有独立价值；
3. 复杂表格视觉审核是频发风险还是少量边缘情况。

当前优先假设是先提高真实产品覆盖率；只有运营证据推翻这一假设，才优先恢复重型审核治理候选。
