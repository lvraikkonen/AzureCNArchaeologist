# v0.4 分支化、逐阶段执行计划

## 工作方式

- 从已冻结且干净的基线提交 `00e6df5` 创建本地开发分支：

```
git switch -c codex/v0.4 00e6df5
```

- 不直接修改 `master`，不自动 push、merge 或创建 PR。
- P0、P1…P5 各自形成独立实现切片、测试门禁和提交。
- 每个阶段结束后汇报：变更、测试、生成证据、已知失败和 Git 状态；等待用户确认后再进入下一阶段。
- 跨文件修改后，如后续仍依赖代码检索，先执行 `codegraph sync`。
- 任何门禁失败都保留真实失败状态，不创建成功报告、不升级版本、不用 skip/unsupported 掩盖。

## Step 0：创建分支与建立可复现起点

1. 再次确认 `master` clean、HEAD=`00e6df5`。
2. 创建并切换到 `codex/v0.4`。
3. 记录分支基线、Product Index digest、VM 双语源大小/SHA 和当前 49 项 v0.2/v0.3 回归结果。
4. 在分支上建立最小 pytest 前置能力：
   - `pyproject.toml` 声明 pytest dev dependency；
   - strict config、strict markers、仅收集 `tests/`；
   - 将 `uv.lock` 纳入版本控制；
   - 证明现有回归可由 `uv run pytest` 收集并通过。
5. 提交建议：`test: establish v0.4 trusted test entry point`。

完成后暂停汇报，等待确认进入 P0。

## Step 1 / P0：隔离实现并真实导出 `virtual-machines`

### 实现

- 新增 `experimental-extract`，接口固定为：

```
uv run cli.py experimental-extract virtual-machines \
  --language <zh-cn|en-us> \
  --experiment-id <shared-id>
```

- `experiment-id` 必填，匹配 `^[a-z0-9][a-z0-9._-]{0,63}$`；不提供 `both`、输入文件、策略、输出目录或资源上限覆盖参数。
- 新增 closed-world exception schema/config，唯一允许 VM：
  - `owning_team=AzureCNArchaeologist`；
  - 强制 `complex`；
  - 固定双语 Product Definition-resolved source、字节数和 SHA；
  - 8 MiB、900 秒、2 GiB RSS；
  - 输出根 `output/experiments`；
  - 源身份变化或 v0.4 完成时过期。
- 使用父进程 runner 与独立 worker：
  - 父进程验证 Product Definition 仍为 `known_unsupported`、路径、大小、SHA、严格 UTF-8；
  - worker 再验证读取字节并直接执行 `complex`，禁止 auto/`large_file`；
  - `psutil` 监控整个进程树，超时/超限终止；
  - 在临时语言目录生成 candidate 和 Manifest，验证后原子 rename；
  - 已存在的成功语言目录禁止覆盖。
- 失败只保留内部 JSONL 日志；清理该语言的临时/部分 Candidate，不生成失败 Manifest。
- uploader 显式拒绝实验根、`*.unvalidated.json` 和 `trust_status=unvalidated`，即使存在伪造 sidecar。

### 真实执行

使用同一 ID，先中文、后英文，分别运行。每种语言必须真实产生：

```
output/experiments/<shared-id>/<language>/
├── virtual-machines.unvalidated.json
└── experiment-manifest.json
```

Manifest 记录源/candidate 哈希、强制策略、资源数据和固定状态：

```
{
  "trust_status": "unvalidated",
  "approval_eligible": false,
  "publishable": false
}
```

成功文案只能是 `EXPERIMENTAL OUTPUT GENERATED — UNVALIDATED`。任一语言退出非零、缺文件、资源超限或 JSON 不可解析，P0 即失败。

### P0 验收

- 两条真实命令均退出 `0`，四个 JSON 存在且通过 schema/hash 复核。
- `data/prod-html`、`runs/`、Golden、事实基线和 Review Queue 没有 VM 产物。
- Product Definition 仍为 `known_unsupported`。
- upload 针对 candidate、实验目录和伪造 sidecar 均拒绝。
- 向同事交付双语目录、文件 SHA 和 unvalidated 声明。

建议提交：`feat: add quarantined virtual-machines experimental extraction`。实际 Candidate 保持 gitignored，不提交。

完成或失败后暂停；只有真实证据齐全才报告 P0 完成。

## Step 2 / P1：配置、输入与运行能力边界

- Product Definition 升级为 closed-world 1.1；校准并迁移现有 `extraction` 字段，最终未知/废弃字段阻断。
- 正式 `extract` 移除公开 `--html-file`，只接受 Product Definition 与 canonical Normalized Input。
- 正式输入改为严格 UTF-8，保留 BOM，删除 GBK/Latin-1 fallback；charset 冲突形成 Source Quality Finding。
- 增加 Reconstruction Parseability：生产 parser 与独立 parser 比较正文、价格表及关键片段指纹；材料性分歧阻断。
- 生成 v0.4 Planning Baseline Manifest：
  - 明列全部 434 项；
  - 固定 v0.3 的 379 个 runnable denominator；
  - 自动检查只能提出 delta，不能自行缩小分母。
- 新增 Validation Profile、Applicability Map、Rendering Profile、InMemory Capability Profile 身份，并冻结在 Input/Batch Manifest 2.0。
- 从正式路径移除 `LARGE_FILE` 语义选择和 unknown/error-to-Simple fallback。
- 对最大真实输入与 5 MiB 近上限样例各运行三次隔离确定性测试，按证据冻结最终 in-memory ceiling；超限只允许形成 reviewed planned-non-runnable delta。

建议提交：`feat: freeze v0.4 input and capability boundaries`。

通过 P1 测试、379/379 accounting 和 profile 重放测试后暂停。



## Step 3 / P2：CMS 契约与筛选状态

- 保持 Flexible 1.1 / SupportArticle 1.0 Business Payload wire shape，增加严格语义验证层。
- 嵌套 JSON 使用 deterministic canonical serialization。
- 验证：
  - filter domain 非空、key/value 唯一；
  - 首项为默认状态；
  - CMS state space 等于 filter domains 笛卡尔积；
  - 每个状态恰好命中一个 active、非空、price-bearing group；
  - criteria 包含全部 filter keys，每 key 一个声明值；
  - 无 wildcard、多值、inactive、placeholder、stale 或 `sharedContent`；
  - `sortOrder` 正整数、唯一、物理顺序升序。
- 严格执行 Simple/RegionFilter/ComplexFilter Page State Machine。
- 双语 label 可本地化，但机器 key、value、默认状态和状态顺序必须一致。

建议提交：`feat: enforce v0.4 cms state contracts`。

表驱动 unit/component 测试和四个 Core 产品的状态契约测试通过后暂停。

## Step 4 / P3：Pricing Fact Fidelity

- 建立 `ReachableSelectionState`、`CanonicalPricingTable`、`PricingFact`、`FactInventory`、`SourceFinding`、`EvidenceReference`。
- Source 和 Payload 使用独立 collector，只共享数据类型与经独立测试的最小归一化原语。
- Source 侧通过 Applicability Map 生成 Expected Inventory；Payload 侧按 CMS 契约回读 Observed Inventory。
- 按 canonical state 分区比较多重集合，保留重复次数；同时比较显示文本、数值、币种、单位、周期、区间、层级表头、label、限定、脚注和状态归属。
- 展开 `rowspan`、`colspan` 和多层表头；上下文或 applicability 无法证明即验证失败。
- Expected Publishable Text 要求 100% state-aware coverage。
- Explained Orphan 告警；Unresolved Orphan 阻断批准；导入任何 orphan 直接失败。
- Expected/Observed/Diff 写入 gitignored、无 Run ID/时间字段的确定性子证据。

建议提交：`feat: add source-driven pricing fidelity validation`。

独立 collector、复杂表格、multiplicity、状态错配、orphan 和 Core Pricing baseline 校准测试通过后暂停。

## Step 5 / P4：Report 2.0、批准阻断和视觉门禁

- 新批次使用 Machine Validation Report、Review Queue、Batch Report 2.0；旧 1.x 仅保留只读兼容。
- 每个冻结 runnable item 都生成 Report 2.0，包括 normalize/preflight/extract 失败项；不存在缺报告或 indeterminate。
- Report 分区记录 input、parseability、contract、state、publishable text、pricing fidelity、source findings、profile/map identity、`approval_eligible` 和 `approval_blockers[]`。
- Machine-pass 项均进入 Review Queue；queue membership 不代表可批准。
- 新增受控 Source Finding Disposition、Visual Review Evidence 和 review decision 命令；machine failure 或任一 blocker 存在时拒绝 `approved`。
- 正式 upload 同时要求 machine pass、`approval_eligible=true` 和 `review=approved`。
- 冻结 Desktop 1440×900、100% zoom、DSF 1 的 Rendering Profile，并记录 Chromium、字体、模板、CSS 哈希。
- 为 `cloud-services` 双语生成源/Payload 视觉证据；展示给用户，仅在明确人工 verdict 后记录结果。

建议提交：`feat: add machine validation reports and approval gates`。

双语 `cloud-services` 视觉审核及 blocker 防绕过测试完成后暂停。
