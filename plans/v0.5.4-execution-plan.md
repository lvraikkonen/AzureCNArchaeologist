## 1. 目标、保证边界与非目标

v0.5.4 只完成以下四项：

1. 证明生产 `SupportArticleStrategy` 丢失直接文本的共享代码机制，并在通用 `mainContent` sibling serializer 中修复；
2. 保留首个 `h2` 到当前 parent 末尾的既有正文 boundary，同时按物理顺序保留业务元素和非空直接文本节点；
3. 用真实双语 ICP、ICP/SLA/LEGAL/PSR family 回归、controlled counterexamples 和新 full bilingual Batch 证明修复准确且没有非预期目录级回退；
4. 在新 Batch 上复用现有 Independent Fidelity 1.1 engine，为双语 `icp-faq` 和一个既有 SLA witness 生成窄 formal Evidence slice，经人工接受后完成版本收口。

以下保证边界始终成立：

- L3a 与 L3b 继续作为独立 claim 并行展示；Machine Gate 保持 accepted `parallel_only`、`runtime_effective=false`；
- L3b oracle 不调用或共享生产 Strategy、serializer、cleaner、URL rewriter、payload builder 或 production reconstruction helper；
- `en-us/icp-faq` 继续声明其复用中文 Source，只证明对实际 binding 的 fidelity，不证明英文翻译或本地化质量；
- Business Payload 不增加 validation、Evidence、source、quality 或运行 metadata；
- Workbench 继续 GET-only 展示现有 Evidence 1.1，不新增人工 L3b lifecycle，不写 L4 Review Decision；
- 不 build Release、不 upload、不 publish、不 push、不 merge、不创建 PR；
- 不修改历史 Batches、accepted reports、Evidence 或 tags。

本版本明确不做：

- 不增加 `v054_*` Independent Fidelity 平行模块、target set、Profile、Schema、algorithm identity 或 compatibility facade；
- 不重命名或泛化现有 `v053_*`；完整架构收敛留给 v0.6 前的多 Agent code review；
- 不改变 `articleDescription`、title/metadata、SupportArticle strategy selection、route-map 语义、UI selector policy 或历史版本选择；
- 不引入新的正文 wrapper 标签，不把裸文本强制包成 `<p>`，不按产品名、问题编号或具体中文文本硬编码；
- 不处理 Simple、RegionFilter、Complex、filter-control、Source ownership 或 catalog exclusions；
- `en-us/time-series-insights` 保持 accepted `not_qualified`，由 R5/v0.6 处理；v0.5.4 不缩小其既有问题，也不为它伪造 bundle；
- 不激活 L3b Machine Gate。

## 3. 修复语义

### 3.1 保持不变的 boundary

生产 SupportArticle 正文继续使用：

- root：既有 `_find_content()` 的 `div.pure-content` → `body` → document fallback 语义保持不变；
- start：root 内首个 `h2`；
- end：该 `h2` 的 parent 末尾；
- cleanup：组装完整 fragment 后移除既有 UI selectors，再执行既有 URL rewrite；
- empty behavior：没有首个 `h2` 或清理后无业务内容时保持现有行为。

v0.5.4 不借 direct-text 修复重新裁定 `.pure-content` fallback、正文起止点、common section ownership 或 UI policy。

### 3.2 新增的 sibling preservation rule

从首个 `h2` 到 parent 末尾逐 sibling 处理：

1. `Tag`：保持现有 clone 行为；
2. `NavigableString` 且不是 `Comment`：若 `str(node).strip()` 非空，按原内容 append 一次；
3. 纯空白 sibling：继续忽略，避免无业务意义的格式 churn；
4. 顶层 `Comment`：继续不进入 Business Payload；
5. 所有 retained nodes 保持 Source 物理顺序，不按文本内容去重、不排序、不移动到相邻 Tag 内；
6. 不 strip、collapse 或重新包装 retained direct text 本身；显著性判断只决定是否保留，不改变被保留内容。

修复必须位于共享 SupportArticle serializer/extractor 边界，生产实现不能包含产品、语言、问题编号、答案内容或其他 item-specific 分支。测试名称、fixture 和断言允许明确引用 `icp-faq`、问题 18/19 及其真实文本，以便锁定已证明的故障形态；这种测试特指不构成生产硬编码。

### 3.3 独立 oracle 保持不变

`src/independent_fidelity/v053_adapters.py::SupportArticleAdapter` 已独立保留非 Comment、非空白 `NavigableString`。v0.5.4 不从生产代码调用它，也不把两边抽成共享 helper。否则 L3b 会失去发现共同实现错误的能力。

direct-text 修复不改变：

- `schema_version` 1.1；
- Profile `v0.5.3-independent-fidelity-four-family`；
- `independent-four-family-reconstruction-v1`；
- `independent-cms-wire-v2`；
- `independent-content-comparison-v2`；
- transform rule IDs、scope key、payload locator、Basis 或 Evidence semantic identity 算法。

现有 `v053_*` 模块名、CLI 名、Profile ID 和 Basis ID 前缀表示这套四页面族验证契约的引入来源，不表示 Evidence 只能绑定 v0.5.3 Batch。新 bundle 的 current identity 仍由新 Batch、producer、Source/Product Definition/config/payload bindings 和既有算法身份共同确定；v0.5.4 acceptance report 必须明确这是原样复用既有 contract，而不是把旧 Batch Evidence 当作新 Evidence。

如果实现必须改变其中任何一项，立即停止并回到 plan review；不得为了编号对齐机械创建 v0.5.4 successor。

## 4. 测试与回归设计

### 4.1 高信号 serializer tests

新增耐久行为测试，例如 `tests/test_support_article_mixed_content.py`，至少覆盖：

- `<h2/>text<h3/>`：首个 heading 后直接文本；
- `<h3/>text-before<br/>text-after<h3/>`：同时覆盖 `<br/>` 前后直接文本和当前真实故障形态；
- `text<a/>text` 与 text/element/text 多次交错，验证 DOM 顺序；
- 两个内容相同的直接文本节点均保留，验证不按值去重；
- direct text 中的原始有意义空白不被 strip/collapse；
- 纯空白 siblings 与顶层 Comment 不引入 payload churn；
- UI-only tags 仍被移除；
- retained anchors/assets 仍按既有 route-map/URL 规则改写；
- 无 `h2`、空正文和 cleanup 后空正文的既有行为不变。

测试应直接断言输出内容、顺序和出现次数，不以 fragment SHA 代替行为断言。

### 4.2 真实 Frozen HTML tests

真实输入至少覆盖：

- `zh-cn/icp-faq`、`en-us/icp-faq`：Source 中完整答案在 payload `mainContent` 精确出现一次，位于问题 18/19 之间；
- ICP、SLA、LEGAL、PSR 各选择一个双语、当前 supported 的代表 input，验证正文语义、顺序与 URL 未回退；优先复用 `icp-faq`、`sla-summary` 或 `sla-sql-data`、`legal-summary`、`psr-summary`；
- 直接读取 repository Frozen HTML/Product Definition，不复制一整份平行 HTML fixture；历史 v0.4/v0.5.3 baselines 不更新。

真实输入测试可以引用已有 manifest/path binding，但不为每个片段增加新的手工 SHA。Source 更新导致测试变化时，应重新审核内容，而不是静默更新 expected 字符串。

### 4.3 L3b controlled counterexamples

复用现有 `SupportArticleAdapter` 与 direct comparison，至少证明：

- 从 otherwise-correct payload 删除一段 retained direct text → L3b failed；
- 将 direct text 移到相邻 heading 后或交换 interleaved node 顺序 → L3b failed；
- v0.5.3 已有 canonical Evidence 只读证明旧 producer 下 L3a passed / L3b failed；v0.5.4 不再模拟旧 Tag-only producer，也不为该历史结论新增 replay fixture。

counterexamples 使用 fixture/temporary objects，不写 canonical run path，不新增 mutation framework 或 Schema。

### 4.4 两层回归比较

两层比较使用不同输入与不同结论，必须分别记录，不能把 code-only 结论误写成 Batch-to-Batch 结论：

| 层级 | 输入 | 执行阶段 | 必须证明 |
|---|---|---|---|
| 固定输入 code-only impact | v0.5.3 accepted Batch 所绑定的 normalized inputs / Product Definitions；reference 为其 accepted Business Payload，candidate 为修复后提取结果 | P2，正式 Batch 前 | 所有 unaffected Business Payload exact byte-identical；双语 `icp-faq` 只允许 `mainContent` 恢复目标 direct text，其他字段 exact byte-identical |
| Batch-to-Batch current-input comparison | 新 v0.5.4 formal Batch 对比 v0.5.3 accepted Batch | P4，正式 Batch terminal 后 | item membership、status 与 structured error 无未解释变化；payload delta 分离为 producer fix 与 Source/config/input drift，逐项归因并人工接受 |

P2 固定输入检查不做 semantic normalization，也不以“semantic equivalent”替代 exact bytes。对双语 `icp-faq`，报告目标 direct text 的内容、位置和出现次数；对所有其他 items，比较完整 Business Payload bytes。若修复导致 serialization byte churn、非 `mainContent` 字段变化或其他 item 变化，停止并归因，不更新 snapshot 掩盖。

P4 以 `20260812T125640Z-e5aa4b3f` 为直接 reference。其 summary 为 434 total / 383 runnable / 319 extraction-succeeded / 64 extraction-failed / 318 validation-passed / 1 validation-failed / 50 known-unsupported / 1 source-unavailable；这些是比较基线，不是允许通过删减 item 保持的目标数字。新 Batch 的额外 payload delta 必须与 Source/config/input diff 一起展示，不能用“SupportArticle 重序列化”总称豁免，也不能把已归因但尚未人工接受的变化视为通过。

### 4.5 scan、impact 与 comparison 的反工具化边界

P0 结构扫描、P2 固定输入 impact check 和 P4 Batch comparison 必须优先复用现有 manifests、Batch reports、测试 helpers 与普通 file/content diff。允许一次性只读命令、测试内 temporary output 和窄 test-only helper；不得因此新增：

- `v054_*` CLI、持久化 impact manifest、JSON Schema、renderer 或报告生成框架；
- 通用 Batch auditor/comparator、path+SHA inventory、payload fingerprint 或 semantic normalization 层；
- compatibility facade、service layer 或新的生产 abstraction。

检查输出只需覆盖 changed item IDs、changed payload fields、必要 content diff、status/error changes 与逐项 attribution。若现有工具确实无法表达本版本所需的窄断言，先在 plan review 中展示缺口，不在实施中机械扩建工具链。

## 5. P0–P5 实施阶段

### P0：Plan freeze 与可执行性 preflight

1. 用户先复核 architecture preflight；若该报告已独立提交，记录其 commit；若尚未提交，可与本计划和必要 ROADMAP 状态一起进入同一个 Plan freeze commit，不强制制造单独的 preflight commit；
2. 用户接受本计划后形成 Plan freeze commit；该 commit 不含生产代码、Batch 或 Evidence；
3. 确认本地 `v0.5.3` tag、acceptance commit、accepted Batch 和两份 exact negative Evidence；
4. 按第 2.2、4.5 节重跑结构扫描并记录 expected affected item IDs；
5. 确认三个 repair-slice targets 仍在现有 target set，Profile/algorithms/Workbench reader 未漂移；
6. 运行 historical v0.5.2 verify，并严格按第 6.2 节执行一次 v0.5.3 expected-nonzero verification；
7. 复核 Batch/Evidence 的 producer provenance 仍以 git commit 与现有 manifest binding 为权威。当前实现没有独立 `package_version` producer field，但 `pyproject.toml`、`uv.lock` 的文件 bytes/SHA 已进入 immutable repository provenance：package version 不单独参与 identity/binding 时保持 P4→P5 顺序；若核实为仅被持久化展示而不参与信任边界，在报告中明确其语义；若现有 contract 已改为要求 package version 与 release version 一致，暂停并回到 plan review 调整 version-bump 时点。不得因此新增 package-version identity、SHA、Schema 字段或 compatibility mapping；
8. 不改代码、不生成新 Batch、不生成 canonical Evidence。

### P1：先证明根因的高信号测试

1. 添加第 4.1–4.3 节测试，证明旧 Tag-only loop 会丢失 direct text；
2. 对真实双语 `icp-faq` 锁定正文、相邻节点顺序和出现次数；
3. 锁定纯空白、Comment、UI cleanup 与 URL rewrite 的非目标行为；
4. 确认生产行为不依赖产品名、语言、问题编号或答案分支；测试可按第 3.2 节明确命名 `icp-faq` 和问题 18/19，但不修改历史 baselines；
5. 此阶段只使用 test temp paths，不写 `runs/*/independent-fidelity`。

### P2：最小生产修复与 family regression

1. 在 `SupportArticleStrategy._extract_main_content()` 或同一生产职责边界实现第 3.2 节规则；
2. 不新增通用 DOM framework、serializer service、compatibility wrapper 或 `v054_*`；
3. 保持生产和独立 oracle 无实现依赖；
4. 运行 serializer、真实双语、四 family、route-map、pipeline/validation 定向测试；
5. 使用 v0.5.3 accepted normalized inputs，按第 4.4、4.5 节运行固定输入 code-only impact check；
6. 证明所有 unaffected Business Payload exact byte-identical；双语 `icp-faq` 只允许 `mainContent` 在目标位置恢复 Source 中的 direct text，其他 payload 字段 exact byte-identical；
7. 若出现额外 item、字段或 byte delta，先归因并判断是否仍属于同一规则；不能引入 semantic normalization，也不能直接更新快照让测试变绿。

### P3：implementation commit 与完整门禁

1. P1–P2 开发工作树完成后，只运行全部定向测试、固定输入 SupportArticle impact check 与 `git diff --check`；
2. 提交 production fix/tests，记录 implementation commit；
3. 在该 committed HEAD 上运行第 7.2 节完整 clean-tree gate 一次；
4. 完整门禁通过且 worktree clean 后，把该 implementation commit 作为唯一 formal producer candidate；
5. **P3 完成前禁止正式 pipeline Batch 和 canonical Evidence。**

文档或测试结果不能替代 clean producer commit。若 producer commit 之后有任何 verdict-relevant 代码、Profile、config 或 Source 变更，必须重新通过适用门禁并产生新的 Batch；不能继续沿用旧 producer identity。

### P4：正式 full Batch、窄 Evidence slice 与人工复核

从 P3 clean implementation commit 运行：

```bash
uv run cli.py pipeline-run --all --language both --parallel-jobs 6
```

禁止 `--allow-dirty`。Batch terminal 后：

1. 冻结 Batch ID、producer commit、input manifest、current batch manifest、actual item/status/error denominator 和 Business Payload bindings；
2. 按第 4.4、4.5 节执行 Batch-to-Batch current-input comparison；在正式 record 前解释任何 preflight affected set、item/status/error、Source/config/input 或 formal scope 变化；
3. 只使用现有 per-item CLI 为三个 repair-slice items record：

```bash
uv run python scripts/v053_independent_fidelity.py record \
  --batch-id <v0.5.4-batch-id> --item-id zh-cn/icp-faq
uv run python scripts/v053_independent_fidelity.py record \
  --batch-id <v0.5.4-batch-id> --item-id en-us/icp-faq
uv run python scripts/v053_independent_fidelity.py record \
  --batch-id <v0.5.4-batch-id> --item-id zh-cn/sla-sql-data
```

4. 每个 bundle 生成后立即 per-item verify；预期全部 `canonical_bundle_verified`、1/1 passed；
5. 对同一三个 items 第二次 record，必须返回 `existing-current/read-only`，且各 target bundle inventory 不变；
6. 再次严格按第 6.2 节只读 verify v0.5.3 historical set；

## 9. 暂停与停止条件

出现以下任一情况，停止当前实施并回到 plan review：

- Plan freeze 后 affected identity/family、正文 boundary 或 mixed-content ownership 实质扩大；
- 修复需要改变首个 `h2` boundary、`articleDescription`、UI policy、route-map 或 Product Definition contract；
- 必须修改 Independent Fidelity adapter/verifier、Profile、target set、Schema 或 algorithm identity；
- 必须新增 `v054_*`、compatibility facade、共享生产/oracle helper 或通用 serializer framework 才能继续；
- 真实测试发现 direct text 在 UI-only/ambiguous ownership boundary，无法证明应进入正文；
- full Batch 出现双语 ICP 之外的未解释 Business Payload delta，或 item status/error regression；
- 任一新 formal bundle failed/blocked、binding fatal、stale/corrupt 或缺失；可信负证据必须保留，但版本 No-Go；
- v0.5.3 historical Evidence identity/bytes/verification 发生变化；
- 用户要求在 v0.5.4 激活 Machine Gate、写 L4 或进入 Release/publication；
- formal producer 不是 committed clean HEAD，或完整门禁失败。

正常 Source/config 更新不自动要求重写整份计划，但必须在 P0/P4 显示其对 affected set、actual scopes 和 payload delta 的影响。无法归因时停止，不通过缩小分母或更新 snapshot 掩盖。

## 10. 建议提交顺序与 v0.5.5 handoff

1. **Plan freeze**：获接受的本计划与必要 ROADMAP 状态，不含代码、Batch 或 Evidence。architecture preflight 若已独立提交则记录该 commit；若尚未提交可包含在本次 freeze commit，不强制拆分；
2. **Implementation / formal producer**：production serializer、tests 与必要测试数据引用；提交后完整门禁通过的 commit 是唯一 producer provenance node；
3. **Evidence/report candidate**：新 full Batch、三个 canonical bundles、regression/comparison/acceptance/handoff candidates；该 commit 不升级版本、不创建 tag；
4. **Acceptance/version/tag**：人工接受后更新版本与状态，提交 acceptance/version commit，在其唯一一次完整门禁通过且 worktree clean 后创建 tag。

必须保留的顺序性 provenance nodes 只有 Plan freeze、formal producer implementation、Evidence/report candidate、acceptance/version + tag。architecture preflight 可以有独立 commit，但不是被本计划强制新增的第五个节点；不得合并 producer 与 Evidence candidate，也不得在人工接受前生成 acceptance/version node。

v0.5.5 主题保持 accepted ROADMAP 的 Simple page-global boundary/classification（当前 16 items）。v0.5.4 不得以 SupportArticle 修复为由提前处理 Simple boundary，也不得单方面重排 v0.5.5/v0.5.6/v0.6。
