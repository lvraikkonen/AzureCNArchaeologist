## 摘要

v0.5.1 只建立两类基础：

1. 把 v0.4.1 后当前可运行范围按 reviewed-candidate 流程冻结为 v0.5 Planning/Core successor；
2. 冻结 v0.5.2 `api-management` 正式闭环确实需要的最小 L3a/L3b 契约、输入绑定、历史语义、轻量独立性保护和可人工复核的 Evidence 投影。

v0.5.1 冻结 L3b 与现有机器验证并行存在的声明关系、契约和证据形式；从 v0.5.2 开始，对正式 Batch 并行记录 L3b；v0.5.3 扩大正式覆盖，并裁定 L3b 是否进入 Machine Gate。v0.5.1 不建设大型验证平台，不接入完整 Workbench，不修改 Review、Release、upload 或 Approval Eligibility，也不预先承诺 L3b 成为全局 Machine Gate。

## 1. 目标保证与非目标

### 1.1 必须建立的保证

- Planning Baseline、现有 `input-manifest.json`、现有 `batch-manifest.json` current item/output record 与 L3b Evidence 各自只有一个明确职责，不重复保存同一套输入事实；
- L3a 与 L3b 是两个独立机器声明，分别保存 `claim`、`verdict`、`coverage`、bindings 和 evidence；
- 单个声明只使用 `passed`、`failed`、`blocked`、`not_qualified`、`not_run`，并按冻结的 item-level 规则聚合 required scopes；后三者不得聚合为 `passed`；
- L3b Evidence 精确引用 immutable `input-manifest.json` binding 和 current `batch-manifest.json` revision/output binding，并能追溯到 verifier、重建、wire transform 与 comparison 身份；
- 独立实现不导入或调用生产内容选择、归属、转换执行或 payload 组装路径；
- 最小 Evidence bundle 可生成 inert 的只读并排复核视图，同时不产生第二套审核状态权威；
- Evidence semantic identity 与可重新生成的 review projection artifact identity 分开，展示样式变化不使旧 Evidence stale；
- 历史 Evidence 对其原绑定保持可解释；输入或算法身份变化后不能自动用于当前工作；
- baseline、fixture 与 golden 只通过 candidate、diff、rationale 和 exact SHA 提升。

### 1.2 明确不在 v0.5.1 实现

- 不从正式 Pipeline 调用完整 L3b verifier；
- 不为 `api-management` 生成正式 Batch L3b 结论；该闭环属于 v0.5.2；
- 不冻结完整 desktop/mobile state universe 或未来页面家族专用 Schema；
- 不冻结完整 Machine Gate activation policy；
- 不接 Workbench、Review Decision、Approval Eligibility、Release Manifest 或 upload；
- 不定义历史 Release 回填方式；
- 不新增 `manual_l3b_passed`、`manual_l3b_failed`、`manual_l3b_pending` 或任何人工 L3b lifecycle；
- 不修改 Business Payload Schema，不把诊断信息写入 payload；
- 不修复 C1–C9、上游 HTML 或 `soft-category.json`；
- 不改写 accepted v0.4.1 Batch、tag、baseline、fixture、报告或既有实验输出。

## 2. Artifact 职责与绑定链

本文中的 `Batch/Input Manifest` 是对现有 Batch 绑定信息的**逻辑统称**，不要求新增第三份 Manifest，也不要求把 output identity 写入不可变的 `input-manifest.json`。

| Artifact | 唯一职责 | 不负责 |
|---|---|---|
| v0.5 Planning Baseline | 计划范围、runnable/skip 状态、分母、逐项变化理由和 predecessor | 保存每次运行的全部输入 SHA 或 L3b 比较结果 |
| `input-manifest.json` | 继续保存本次运行的 Source、Normalized Input、Product Definition、适用 config/route map 等不可变输入身份；可以包含计划 artifact route，但不保存 realized payload SHA 或 Batch revision | 承担 current output identity 或在运行后被回写 |
| `batch-manifest.json` current Batch Item / output record | 继续保存 Batch revision，以及 persisted payload 的 current path、SHA 和 output record | 成为第二份输入清单或重写 `input-manifest.json` |
| L3b Evidence | 同时引用 immutable input binding 与 current Batch revision/output binding，补充 verifier profile、状态重建、允许转换和比较结果 | 成为第二份 Planning Baseline、第三份 Manifest 或完整复制 Batch 输入事实 |

`Reconstruction Basis` 保留为逻辑概念：它由 `input-manifest.json` identity、`batch-manifest.json` current revision/output record、适用的 profile/version 以及本次状态定位/criteria 组成。v0.5.1 不再建立一份与现有 Manifest 重复的巨型 `Reconstruction Basis Manifest`。

绑定链固定为：

```text
Planning Baseline（计划范围）
  → input-manifest.json（不可变输入身份）
    → batch-manifest.json / output record（current revision 与 persisted payload 身份）
      → L3b Evidence（独立重建、比较与逐状态证据）
```

## 3. L3a、L3b 与状态语义

| 声明 | 证明范围 | v0.5.1 处理方式 |
|---|---|---|
| L3a：策略重放一致 | persisted payload 与现有生产路径重放结果一致 | 保留现有证据，明确其保证范围，不称为独立源保真 |
| L3b：独立源内容保真 | 不调用生产选择/归属/转换执行实现，从正式输入独立重建并比较 persisted payload | 冻结最小契约、资格、绑定和可复核投影；v0.5.2 首次正式运行 |
| Machine Gate | 将来可能汇总所需机器声明的 policy | 当前 policy 保持不变；v0.5.3 基于正式证据裁定是否及如何启用 L3b |

单个声明状态定义：

| 状态 | 精确定义 |
|---|---|
| `passed` | 声明适用，声明覆盖范围全部完成，且无 mismatch 或 blocking error |
| `failed` | 比较已执行，至少一个被比较对象与预期不一致 |
| `blocked` | 声明原本适用，但输入、依据、状态身份、payload 或执行条件不足，无法得出结论 |
| `not_qualified` | 当前 verifier profile 未声明支持该页面或结构；不是成功，也不是执行错误 |
| `not_run` | 尚未调度或尚未产生结果 |

### 3.1 Item-level verdict 聚合

先判定执行前资格/调度状态；一旦 verifier 开始执行，item verdict 只能在 `failed`、`blocked`、`passed` 中聚合：

| 条件 | Item verdict |
|---|---|
| profile 在执行前不支持该 item | `not_qualified` |
| 从未开始执行 | `not_run` |
| 任一 required scope 已确认 mismatch | `failed` |
| 没有 mismatch，但至少一个 required scope 无法完成，或 verifier 启动后发生执行错误 | `blocked` |
| 所有 required scopes 均完整完成且通过 | `passed` |

已执行结果的优先级固定为 `failed > blocked > passed`。例如状态 A `failed`、状态 B `blocked` 时 item 为 `failed`；verifier 启动后的异常为 `blocked`，不得退回 `not_run`。`not_qualified`、`not_run` 是执行前的 item 结果，不与已经执行的逐状态结果混用。

L3a 与 L3b 可以产生不同 verdict，但不形成两个互相竞争的生命周期权威。人工复核 L3b Evidence 后的正式决定继续写入现有 L4 Review Decision 与 `inspected_states`。

## 4. 实施顺序

### P0：冻结 v0.5 入口基线

#### P0.1 保留历史权威

- accepted v0.4.1 Batch、tag、报告、Planning/Core baseline 与 fixture 保持不可变；
- accepted v0.4.1 Batch 只作为 predecessor 和防回退参照；首份正式 L3b Evidence 绑定 v0.5 successor/reference Batch，不向 v0.4.1 回填；
- v0.5 只写入明确的 successor 路径，并记录 predecessor ID/SHA；
- 不把新输入、golden 或 verdict 写回 v0.4 命名空间。

#### P0.2 建立 v0.5 Planning Baseline candidate

候选必须逐项表达 434 个语言级计划项：

- 383 个 reviewed runnable；
- 50 个 `known_unsupported`；
- 1 个 `source_unavailable`；
- accepted v0.4.1 的 379 runnable 到当前 383 runnable 的逐项变化；
- `cdn`、`data-transfer` 四个新增 runnable 语言项的 prior/proposed state、资格证据、Product Definition decision、分母影响和 rationale。

Planning Baseline 不复制每次运行的 Source/config/payload SHA；实际输入身份由 immutable `input-manifest.json` 保存，realized payload identity 和 Batch revision 由 current `batch-manifest.json` item/output record 保存。提升流程必须包含 candidate、逐项 diff、rationale、人工接受和 exact SHA promotion；普通运行不能自动接受 capability delta。

#### P0.3 建立 v0.5 Core successor

- 以当前 Core candidate 证据建立 v0.5 successor，不覆盖 v0.4 fixture/baseline；
- Core 保持 4 产品 × 2 语言，单独审核 `cloud-services` 双语 Source 与 `soft-category` 身份变化；
- 先审核并提升 fixture candidate，再执行两次 clean Core run；
- 为输出生成 baseline candidate，审核输入绑定、payload/semantic diff 与 candidate SHA；
- 仅允许 exact SHA promotion，并生成排除运行级 metadata 的 determinism record。

#### P0.4 冻结完整双语 reference Batch

在 v0.5.1 最终 clean commit 上运行：

```bash
uv run cli.py pipeline-run --all --language both --parallel-jobs 6
```

该 Batch 必须：

- 按 434 / 383 / 51 完整对账；
- 允许真实结构问题导致 `completed_with_failures`，但不允许 unexplained queue gap 或缺少稳定诊断；
- 同时绑定 immutable `input-manifest.json` 输入身份和 current `batch-manifest.json` revision/output record；
- 列出相对 accepted v0.4.1 Batch 的 outcome 和输入/产物变化；
- 只作为当前 execution/L3a reference，不产生 L3b 正式结论；
- 为 v0.5.3 后重新裁定 v0.5.4–v0.5.6 问题组顺序提供参考。

### P1：接受最小 ADR

只记录实现前必须稳定的决策，不建立通用验证治理体系：

1. L3a/L3b 是并行机器声明；当前 gate policy 不变，v0.5.3 才根据正式证据评审 L3b 门禁；
2. 三类逻辑 artifact 的职责、现有 input/batch manifest owner、Evidence 与 persisted payload 的 current binding、历史 Evidence 语义和独立实现边界。

可按既有 ADR 粒度拆成两个相邻 ADR；若一个 ADR 已能清晰覆盖，不为形式增加第二个。ADR 只收窄冲突的既有表达，不提前冻结 Workbench、Release 或未来页面家族接口。

### P2：冻结最小 Evidence 契约

保留三个逻辑概念，但只冻结 v0.5.2 `api-management` 正式消费者必需的字段；不要求提前形成三个完整 production-grade Schema：

1. **Independent Fidelity Profile**：`schema_version`、profile ID/version、适用资格、允许/禁止依赖，以及三个 verdict-relevant algorithm version；
2. **Reconstruction Basis**：`schema_version`、immutable input-manifest identity、current batch-manifest revision/output record、item/state 身份、locator/criteria，以及适用的 `soft-category`/route-map 引用；
3. **Independent Fidelity Evidence**：`schema_version`、逐状态结论、hash、片段引用、diff、错误、semantic identity 与 projection artifact identity。

任何独立顶层契约都必须包含自身的 `schema_version`。它只是契约演进版本，不是第四类算法版本。最小 Evidence 字段为：

```text
schema_version
claim
verdict
coverage
batch / item / language / resource identity
source identity
product definition identity
soft-category / route-map identity（适用时）
persisted payload identity
verifier profile/version
reconstruction_profile_version
wire_transform_version
comparison_version
per-state identity
source / expected / payload / diff references
per-state source / expected / payload hashes
per-state applied_transform_rule_ids
locator / criteria
retained / removed table IDs（适用时）
blocking errors / mismatches
evidence_semantic_identity
review_projection_artifact_identity
```

两类 identity 的边界固定为：

- `evidence_semantic_identity` 从 Reconstruction Basis、Source/Expected/Payload hashes、`applied_transform_rule_ids`、verifier profile、三类算法版本、claim/coverage/verdict 和 blocking errors/mismatches 的 canonical semantic object 计算；任一语义输入变化都会改变它；
- `review_projection_artifact_identity` 绑定由该 Evidence 生成的 `review.html` 和 display-only diff projection；`diff.html` 排版、CSS 或 `review.html` 布局变化只改变 projection identity，不改变 semantic identity，也不使旧 Evidence stale。

对已冻结的最小字段使用 closed-world 校验，并覆盖缺字段、额外字段、错误 enum、错误引用/hash 等基本负例。以下内容明确延期到真实消费者证明需要时再决定：

- 完整 desktop/mobile state universe；
- 完整 Machine Gate activation policy；
- Workbench 完整交互契约；
- Release Manifest 绑定结构与历史 Release 回填；
- 大量未来页面家族专用字段。

### P3：建立轻量独立性保护

独立 L3b 包不得导入或调用：

- 生产 Strategy；
- `ExtractionCoordinator` / `StrategyManager`；
- Source Reachability Resolver；
- Source Content Projector；
- Region Processor；
- 生产 HTML cleaner；
- payload / `contentGroups` builder；
- 生产允许转换的执行实现。

v0.5.1 只交付：

1. 一个静态 import/dependency 检查；
2. 一个 runtime sentinel/smoke test，证明最小重建/比较路径不会触发被禁止入口。

允许共享的内容限于冻结字节的安全读取、SHA/canonical JSON、第三方 HTML parser 和无内容选择职责的纯比较模型。即使共享 transformation rule ID，独立侧也使用独立执行实现。不建设通用依赖治理框架；独立性还必须由 P5 的反证测试证明。

### P4：冻结三类算法身份与历史语义

只有真正影响 verdict 的三类版本进入契约：

1. `reconstruction_profile_version`：locator、状态重建、内容归属、状态顺序和 suppression；
2. `wire_transform_version`：允许的 CMS 线格式或语义物化转换；
3. `comparison_version`：raw/DOM/标签结构/可见文本比较与规范化。

diff 展示格式只影响人工阅读，不单独版本化为 verdict 身份，也不导致历史 Evidence 失效。

历史规则保持最小且单向：Evidence 对其原 immutable input-manifest binding、current-at-creation batch-manifest revision/output binding、profile 和三类算法身份仍是合法历史记录；任一当前 semantic binding 变化后，旧 Evidence 不能自动用于当前 Review、Release 或问题组验收，但不删除、不重写。仅有 review/diff 展示变化不影响这项资格。v0.5.1 只冻结并测试这项语义，不建设复杂 evidence lifecycle、历史 Release 回填或 gate 迁移系统。

### P5：最小反证集合

使用人工可读 fixture，并只在内存或临时目录注入错误。必须证明：

1. 交换两个状态内容、保持原 criteria 时，L3b 失败；
2. 少选一个源节点时，L3b 失败；
3. 多选一个相邻节点时，L3b 失败；
4. 已声明 wire 转换通过，未声明的同类转换失败；
5. 可以构造 `L3a passed / L3b failed`。

另以参数化 item-level 聚合测试覆盖第 3.1 节全部规则，包括 `failed + blocked → failed`、无 mismatch 但 scope 未完成或启动后异常 `→ blocked`、全部 required scopes 通过 `→ passed`，以及执行前的 `not_qualified` / `not_run` 不与已执行结果混用。FAQ/SLA 越界、配置重复、table ownership、aggregate suppression、隐藏 software 和复杂 hash 漂移矩阵随 v0.5.2/v0.5.3 的真实页面覆盖逐步增加，不作为 v0.5.1 入口条件。

### P6：冻结可人工复核的最小 Evidence 投影

Evidence bundle 使用轻量、可移植的相对引用：

```text
independent-fidelity/
├── evidence.json
├── fragments/
│   ├── state-001.source.html
│   ├── state-001.expected.html
│   ├── state-001.payload.html
│   └── state-001.diff.html
└── review.html
```

`evidence.json` 保存 semantic/projection identity、SHA、verdict、`applied_transform_rule_ids`、错误和相对引用，不内嵌大段 HTML。Source、应用声明转换后的 Expected、persisted Payload 与 diff 必须分别保留，不能只保存最终 DOM。

v0.5.1 用受控 fixture 证明该 bundle 可以确定性生成只读静态 `review.html`，至少可展示：

- 产品、语言、状态身份与上一/下一状态导航；
- filter criteria / locator；
- Source / Expected 与 Persisted Payload 并排片段；
- diff、retained/removed table IDs、实际转换规则与各类 SHA；
- L3a/L3b verdict、blocked reason 或 qualification limitation。

Source、Expected 和 Payload fragment 是证据字节，review renderer 不得把它们直接注入可执行 DOM；必须以 escaped text 或等价 inert/sandboxed 方式展示。打开 `review.html` 不得执行 fragment 中的 script、事件处理器、表单提交或导航，也不得产生外部网络请求。该要求只约束只读投影安全边界，不引入安全平台或托管能力。

该投影不修改 Batch、不写 Review Decision、不改变 Approval Eligibility、不激活 Release gate、不要求数据库/前端框架/托管/多用户能力，也不新增生命周期状态。v0.5.2 才为正式 Batch 的 `api-management` 生成第一份可使用的逐状态只读报告；v0.5.3 再接入现有 Workbench。

1. v0.5 Planning Baseline successor 完整对账 434 / 383 / 51，四个新增 runnable 语言项有独立审核证据；

- 434 / 383 / 51 计划无法逐项重建；
