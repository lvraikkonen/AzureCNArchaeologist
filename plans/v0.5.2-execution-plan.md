## 4. 实施顺序

### P0：Formal target preflight

实现一个只读 binder，先于任何 bundle 写入执行：

2. 重新计算第 2 节全部文件 SHA，验证 input manifest Schema、Batch status、revision `1483`、item execution/output record 与 validation artifact bindings。
3. 证明 Source 与 Normalized Input 均匹配 frozen SHA；不得用 repo 中同路径但不同字节的“当前文件”替代。
4. 证明 payload 存在、为 JSON object、字节 SHA 与 current output record 一致。
5. 读取 L3a validation、sampling plan 和 sampled-content evidence，验证其 artifact SHA、payload/source binding、stored claim/verdict，以及 5/5/0 coverage。

Binder 接受 target 后再独立执行 profile qualification。Profile 正式判定 `not_qualified` 时不产生 bundle；无法建立 trustworthy manifest authority 时不猜测、不写半成品，命令返回 fatal exit 1 且不声称正式 verdict。item 已被准确调度并进入 verifier、binding 已可信后发生的可表达输入不足按既有规则生成 immutable `blocked` bundle，不得回退为 `not_run`。

### P1：独立重建 `api-management` 5 个状态

在 `src/independent_fidelity/` 中扩展正式 consumer，复用安全 byte/SHA/canonical JSON、BeautifulSoup 和现有 contract/bundle 代码，但不复用实验模块或生产选择逻辑。实验代码只作为测试预期来源，不成为 runtime dependency。

重建规则冻结为：

1. Source 中必须唯一定位 `div.technical-azure-selector.pricing-detail-tab`；该 root 内必须唯一定位 `div.tab-content`。
2. hidden software control 必须只有一个真实 option，值为 `API Management`；该值映射到配置行真实字段 `os`，两者共同表示同一个 ownership key，不是 `software + os` 两个维度，也不无依据暴露为 payload filter criterion。
3. desktop region control 独占状态 label、物理顺序和唯一 active/default；`default-first` 只由 desktop default 计算。Mobile `select#region-box` 只校验 scoped machine option domain/targets；mobile default marker 缺失、重复或冲突均忽略，不产生 warning、不改变 verdict。Desktop default 不唯一或 mobile domain/target 不一致时 `blocked`。
4. 独立计算 5 个 `[{filterKey: region, matchValues: ...}]` criteria 及 state ID，并与第 2.1 节及 L3a state universe 双向闭集对账。
5. Source content root 必须含且只含当前冻结的 3 个唯一 table ID：`API-Management-preview`、`API-Management-preview2`、`API-Management-gateway`。同 ID 多表、idless 候选、跨 scope 表或多表 wrapper 均阻断。

### P2：Wire materialization、payload 对齐与比较

v0.5.2 复用已冻结的三类版本：

```text
reconstruction_profile_version = independent-state-reconstruction-v1
wire_transform_version         = independent-cms-wire-v1
comparison_version             = independent-html-comparison-v1
```

v0.5.1 已把 `region_filter`、状态顺序、ownership、suppression 和 CMS wire 物化纳入上述 v1 定义；v0.5.2 是该定义的首个正式 consumer，不修改其既有语义。冻结前审计已确认 ADR-0091、v0.5.1 Profile/Schema 和现有 fixture/test **都没有**规定“唯一 exact 行内重复 normalized table ID 必须 `blocked`”；仓库既有 `reports/v0.4/soft-category-upstream-findings.*` 与运行模型已经记录 first-occurrence ordered-unique/nonblocking redundancy。因此本计划可把 warning-only 作为 v1 首次显式边界并补测试，无需 successor algorithm version；该结论不回写或重新裁决历史 Batch/Evidence。若实施反而证明必须改变 v0.5.1 fixture verdict、版本定义或 Evidence closed-world 字段，则停止并回到计划评审，不能静默在同一版本下改变历史语义。

`api-management` 的 5 个 Source fragment 中没有 `icon-tick`、root-relative image、style URL 或 `data-config` asset，因此本 item 的 `applied_transform_rule_ids` 全部必须为 `[]`；不得因为 profile 支持 `css-generated-semantics-v1` 就无条件应用它。`applied_transform_rule_ids` 只记录针对页面内容条件实际触发的声明式 content-affecting rules；基础 HTML parse/serialize 与 whitespace compaction 由 `wire_transform_version` 表达，不重复列入 rule IDs。因此 `[]` 表示没有额外内容规则被触发，不表示完全没有执行 wire materialization。`independent-cms-wire-v1` 不导入生产 cleaner。

payload 对齐规则：

- `contentGroups` 必须恰有 5 项；每项 `filterCriteriaJson` 必须解析为唯一的单 `region` criterion；
- Source-derived criteria domain、顺序和 payload domain 必须闭集一致；无法唯一对齐时 fail-closed，不按数组下标猜测；
- 对齐后比较 `Expected` 与 `contentGroups[].content` 的 raw wire、DOM、tag structure 和 visible text；
- 在唯一对齐状态内确认的缺失、错置或额外内容是 `failed`；Source/payload state domain 无法唯一对齐时属于 state identity 不足，按 Evidence 1.0 fail-closed 为 `blocked`，两者都不得成为 `passed`；
- 逐状态 verdict 聚合继续使用 `failed > blocked > passed`，全部 5 个 required states 通过才是 item `passed`。

正式 happy path 的预期 coverage 固定为：

```json

  "completed": 5,
  "passed": 5,
  "failed": 0,
  "blocked": 0
}
```

- Source desktop control 无法唯一证明 5 个状态、唯一 desktop default、单 hidden software 或闭合 content root，或 mobile machine domain/targets 与 desktop 不一致；mobile default marker 缺失/重复/冲突不是停止条件；
- formal item 出现 duplicate/missing exact `(os, region)` 行、缺失/重复 Source DOM table 或 wrapper ownership 歧义，导致可信 `blocked` bundle 和版本 No-Go；唯一配置行内重复 normalized ID 只按 successor warning policy 处理，不是停止条件；
- 必须导入禁止的生产 Strategy、Reachability、Projection、Region Processor、cleaner、transform executor 或 payload builder；
- 现有 Evidence 1.0 无法表达首个正式 consumer，必须改变 closed-world 字段或历史 v1 algorithm semantics；
- 无法让 formal happy path 5/5 通过，或受控状态交换不能稳定失败；
- 生成 bundle 必须提前修改 Machine Gate、Workbench、Review、Release、upload 或 Approval Eligibility；
- `record` 会覆盖已有 artifact，或无法证明原 reference Batch artifacts 未变；
- 全量门禁出现无法由本 slice 解释的退化。

停止不等于把失败改成 `not_qualified` 或缩小 required state universe。若需要新 clean Batch、Schema successor 或 algorithm version bump，必须先形成显式 plan amendment。

## 8. 建议提交与冻结顺序

本计划文档冻结 commit 完成后，实施建议按以下可审查边界提交：

1. **Plan freeze commit**：只包含最终冻结的 v0.5.2 Execution Plan 与 roadmap 状态，不生成 Evidence；
2. **Verifier implementation commit(s)**：exact Batch binder、`api-management` Reconstruction Basis builder、formal verifier、recorder/verify entry、canonical bundle promotion、review projection及相应测试；最后一笔 clean implementation commit 的 exact SHA 是正式 Evidence producer identity；
3. **Evidence/acceptance candidate commit**：由 clean implementation commit 运行 formal record/verify，提交 immutable Evidence、acceptance candidate 和 v0.5.3 handoff；不得预写 accepted；
4. **Acceptance/version/tag commit**：exact Evidence 与 candidate 获人工接受后更新版本和 acceptance 状态；clean-tree gate 通过后由本地 annotated `v0.5.2` tag 指向该 commit。

每笔提交只包含一个可独立复核的主题。`d197ef2...`（v0.5.1 accepted/final）、`68fc8fa...`（reference Batch producer）、未来 verifier implementation 和 acceptance/version/tag 四类 identity 必须分别记录。正式 Evidence 只能在实现 commit 已提交且 worktree clean 后生成；acceptance status 不得在 exact Evidence identities 获人工接受前预写为 accepted。
